# ADR-0044: Partition verification inside the existing candidate command and prove first-attempt stability

ADR-0044 is partially superseded by ADR-0045 for candidate/release platform
cardinality and evidence counts. Its deterministic scheduling, bounded
diagnostics, immutable evidence, timeout, LFS, signing, and fail-closed
decisions remain in force.

## Context

Generation 50 passed the complete local suite but failed every hosted operating
system. Ubuntu exposed failures in the 100 MB Git LFS and nested-worker tests,
macOS lost the completed test command at the acknowledgment boundary, and
Windows exposed runtime-binding, temporary-path, file-URL, concurrency-budget,
and LFS representation failures. The existing matrix runs seven closed commands
inside one signed envelope per operating system. Adding retries can hide defects,
and adding workflow jobs or diagnostic artifacts changes the approved trust and
artifact-count boundary.

The feasibility spike confirmed that Vitest supports explicit file filters,
exclusions, pools, `maxWorkers`, JSON reporters, and output files. The existing
Code Graph command already describes and executes 21 deterministic groups.
GitHub's Runs, run-attempts, jobs, and artifacts APIs expose `head_sha`,
`run_attempt`, first-attempt conclusion, per-job `started_at`, and per-artifact
`created_at`, which are sufficient to verify first-attempt adjacency and the
20-minute artifact bound without trusting a self-reported upload duration.

## Decision

Keep exactly the seven existing top-level candidate commands and the existing
one-envelope-per-OS transport. Add a committed canonical execution-plan file as
the sole source of command partitions, pools, worker/fanout slots, and zero-retry
policy. A no-credit three-OS diagnostic run supplies signed region and command
durations; deterministic calibration requires a 3/2 margin and fails rather than
shrinking that margin when the approved individual or aggregate caps do not fit.
The accepted values enter config and are equality-bound to the plan. The
command-plus-formal total cannot exceed 615 seconds, leaving the precondition,
post-condition, and persistence regions inside a 14-minute gate step. The plan,
calibration, and scheduler/launcher digests enter the gate-input fingerprint
before dispatch.

Partition the three test-owning commands internally. Their schedulers and test
launchers share a nonce-bound, all-or-nothing atomic slot-lease ledger under the
private matrix run root and launch only counted groups. Each child reporter
produces a digest-bound partition acknowledgment. The scheduler supplies only a
sorted manifest; the gate-side coordinator independently revalidates every
execution binding, argv, selected-file/worker inventory, report digest, and slot
observation before deriving the one top-level acknowledgment and allowing a
native report into the deterministic aggregate. High-memory LFS,
nested-worker, and real-concurrency groups are isolated; regular tests retain
bounded parallelism. Test-owned child processes move behind repository-owned
counted helpers, so the plan and runtime can detect unbounded fanout instead of
inferring it from hosted-runner behavior.

Adopt one API-job-start-relative deadline. Five pre-terminal workflow steps have
whole-minute maxima of 1 minute for dependency-free full-history Git/LFS fetch
and pointer checkout, 2 minutes for a local preparation action, 14 minutes for
the closed gate, 1 minute for workflow-protected OIDC signing, and 1 minute for
artifact upload. Generation 50's worst observed pre-gate duration was 159
seconds; the no-credit diagnostic workflow must prove maxima of 40 seconds for
bootstrap and 80 seconds for preparation on all three operating systems, so the
fixed steps retain a 3/2 margin. The preparation verifier emits one run-,
attempt-, job-, nonce-, commit-, and API-projection-bound LFS closure manifest
under `RUNNER_TEMP`, and its digest enters the signed result. Gate preconditions
and post-conditions validate that manifest and cheap current-tree probes rather
than repeating full-history scans. The separate workflow-protected signing step,
not candidate code or a writable local action, owns dependency-free failure
synthesis. Upload remains the final one-minute action. The envelope signs
pre-signing timing only. End-to-end
job-to-artifact duration and two consecutive first-attempt successes are
verified externally from current GitHub API metadata and the six OIDC-bound
envelopes, then persisted as candidate-scoped stability evidence. Release
readiness re-fetches the complete projections, so a later rerun or intervening
run invalidates stored evidence. The later run remains the authoritative gate
set.

Keep diagnostic enrichment inside existing `checks[].diagnostics`. Replace
tail-only native-message truncation with bounded head-plus-tail retention and
add only validated plan/runner partition metadata. Existing redaction, entry
count, envelope scalar cap, cause precedence, pass computation, and artifact
count remain unchanged.

## Rejected alternatives

- Retry failed tests or jobs once: rejected because an intermittent first
  failure would disappear from release readiness and contradict the requested
  no-retry policy.
- Reduce the global Vitest worker count only: rejected because it slows all
  tests, does not isolate 100 MB LFS and nested-worker fanout, and does not fix
  Windows path/runtime defects.
- Split partitions into additional GitHub Actions jobs: rejected because it
  increases artifact count, OIDC envelopes, workflow coordination, and release
  ingestion complexity.
- Trust runner-reported total duration: rejected because an envelope cannot
  measure its own signing and upload completion.
- Store raw native reports as another artifact: rejected because it creates a
  new trust surface and can expose unredacted paths or secrets.
- Treat Windows failures as platform exclusions: rejected because the required
  matrix explicitly includes Windows and the failures identify real portability
  defects.

## Consequences

The candidate configuration becomes more explicit and failures become
reproducible by command and partition. Hosted resource contention is bounded
without weakening the corpus or deterministic performance evidence. Two full
matrix attempts increase successful candidate verification cost, but failures
stop after one attempt and are never retried.

Implementation touches the candidate plan/configuration, test-runtime dispatch,
test schedulers, process helpers, portable fixtures, runner timeouts, candidate
result schema, GitHub API stability ingestion, release readiness, diagnostics,
workflow, and associated tests. The direct child-process inventory in tests
requires a broad but mechanical migration to counted helpers. GitHub API
availability and token scope become explicit release-verification dependencies;
missing or inconsistent metadata fails closed.
