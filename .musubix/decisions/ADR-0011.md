# ADR-0011: Separate GitHub Release production from npm publication

## Context

The repository documented a tag-driven release workflow but did not contain
`.github/workflows/release.yml`. Adding a conventional tag workflow that
immediately publishes npm and creates a GitHub Release would bypass the
candidate-bound release approval and operation-specific authorization required
by REQ-M5-RELEASE-001 and REQ-M5-RELEASE-002. Post-candidate evidence cannot be
committed into the immutable tagged candidate without changing its identity.

## Decision

Use two release workflow modes and accept only lightweight release tags, so
GitHub's workflow/OIDC SHA is the exact candidate commit. A pushed `v*` tag
validates the exact tagged candidate and produces a sealed release bundle, but
performs no external release side effect. A later manual dispatch must run from
that same tag, name both `release_tag` and a full-SHA `evidence_commit`, and
provide one explicit release operation ID. Every run
produces and verifies its own run-scoped bundle; the tag-push bundle is
validation evidence and is not reused by a later dispatch.

The evidence commit must descend from the tagged candidate and be reachable
from the repository default branch. The workflow fetches complete history,
derives the default branch from repository event metadata, and rejects squash
or rebase integration that changes the candidate identity. The evidence commit
contains the current candidate-bound release approval and schema-version-2
`status: authorized` operation records. Each authorization binds the Git commit,
release-approval SHA-256, release tag, authorizer, and one operation scope. The
workflow reads that evidence through a separate checkout using validator code
built from the tagged candidate, so neither mutable evidence code nor evidence
files alter the candidate workspace.

The sealed bundle contains the npm tarball, CycloneDX SBOM, `SHA256SUMS`, and a
GitHub-OIDC-authorized ephemeral Ed25519 attestation. The attestation binds the
repository, tagged candidate, release-workflow identity, release mode, release
tag, and checksum-file digest; manual dispatch additionally binds the evidence
commit and release approval. A closed code-defined release transport policy
uses the existing strict attestation verifier without adding mutable
configuration or reusing the candidate-gate workflow identity. Release context
and bundle bindings are represented as canonical digests in equality-checked
`evidenceHeads`. The policy allows 30 days for protected-environment review and
60 seconds of future skew. Every side-effect job independently verifies the
downloaded bundle.

The release workflow creates only the GitHub Release. It validates the release
authorization through the candidate-built read-only API, uses non-cancelling
operation-specific concurrency, rejects an existing Release, uploads every
sealed asset, and writes its terminal outcome only to immutable run artifacts
and the job summary. Candidate snapshot validation accepts the persisted local
candidate commit when it exists and is reachable through any fetched repository
ref, so detached evidence checkouts do not require a same-named local or remote
candidate branch.

Npm publication is a later, separate manual workflow modeled on musubix3. It
requires the stable GitHub Release to exist, downloads its assets, verifies
`SHA256SUMS`, and re-verifies the release-workflow OIDC/Ed25519 attestation
before authenticating to npm or decoding the tarball. Release-document version
surfaces are part of the sealed release contract: source validation checks the
README headlines, upgrade paragraphs, and changelog version heading before
bundle production, while publication checks the same three documents from the
exact downloaded tarball. Only after attestation verification establishes the
asset-to-candidate binding does one bounded extraction pass decode the tarball;
the pass caps decompression and selected-entry sizes and rejects duplicate,
missing, linked, non-regular, or aliased target entries. It validates a distinct
`publish` authorization,
runs the version-existence replay query after artifact and authorization
validation but before any `NPM_TOKEN`-scoped step, and fails closed on an
existing version or an unclassified registry response. All of these steps run
inside one protected `npm-publish` environment job with exactly npm 11.6.0;
only the later authentication, publication, and registry-verification steps
receive `NPM_TOKEN`, and authentication requires `npm whoami`. It publishes the exact downloaded
tarball with provenance and scripts disabled from a directory with no
`package.json`; it never rebuilds or repacks the package. Npm provenance
identifies the publication run, while the release attestation establishes the
artifact-to-candidate binding. Six registry queries, each capped at 15 seconds plus a 2-second forced-kill
allowance,
use 5/10/15/20/25-second backoff under a 240-second wall-clock deadline,
leaving 63 seconds beyond the 177-second timeout-plus-backoff maximum for
process startup and workflow overhead.
The check compares `dist.integrity` with the local tarball SRI and records
whether publication already occurred when a post-side-effect check fails.
Bundle production remains pinned to npm 11.5.1 because changing the pack
implementation would invalidate the approved reproducibility boundary.
Publication uses npm 11.6.0 to match the musubix3 token/provenance transport;
it never repacks, so the differing CLI version cannot alter the sealed tarball.

The sealed GitHub Release also contains canonical `release-context.json`,
covered by `SHA256SUMS` and bound by the attestation. A later publish evidence
commit may add the publish authorization after the Release exists, provided
the attested release evidence commit is its ancestor and the independently
derived release-approval SHA-256 remains unchanged. This avoids requiring
publication authorization before GitHub Release creation without allowing the
Release's approved candidate or manifest to drift.

The GitHub Release side-effect job is dispatch-only and derives expected mode
`dispatch` from its trigger gate rather than from the sealed context. It
independently derives every expected context member, validates the parsed
context schema, and decides context equality solely by comparing the exact
sealed bytes with the canonical encoding of that expected context. No
property-order-sensitive serialization comparison is permitted after canonical
byte equality succeeds.

Publication must complete within the release attestation's 30-day freshness
window. An expired release is not republished under weakened trust; remediation
requires a new candidate and patch-version Release.

## Rejected alternatives

- Publish directly on tag push: rejected because tag authorization does not
  authorize package publication or GitHub Release creation.
- Read evidence from the mutable default-branch head: rejected because the
  release would not be bound to an exact reviewed evidence state.
- Commit post-candidate evidence into the tagged candidate: rejected because it
  changes the candidate that the matrix and release approval attest.
- Keep npm publication inside the release workflow: rejected because a first
  package cannot preconfigure Trusted Publishing, source repacking creates a
  second artifact identity, and unavailable npm credentials must not block the
  independently authorized GitHub Release.
- Publish from a rebuilt source checkout: rejected because the npm registry
  should receive the exact artifact already reviewed and exposed by the stable
  GitHub Release.
- Persist CI completion by pushing another repository commit: rejected because
  it creates a circular push authorization and makes replay state branch-mutable.
- Publish with the token but omit `--provenance`: rejected because it would
  discard the available publication-run supply-chain identity.
- Compare parsed release-context objects by ordinary JSON serialization:
  rejected because property insertion order is not semantic identity and can
  reject canonical byte-identical context.

## Consequences

Release requires an evidence commit on the default branch after the candidate
is integrated and before manual dispatch. Tag-push runs are safe to trigger
without release authorization. Release dispatch carries exact candidate, tag,
and evidence identities, while protected environments remain an additional
control rather than a substitute for repository authorization. Npm publication
cannot begin until the stable GitHub Release exists and a separately authorized
publish dispatch names the exact evidence commit. Successful side effects are
replay-safe through concurrency plus target existence checks, and failed
pre-side-effect runs may be retried with the same still-authorized record.
Bundle nondeterminism discovered before side effects requires a corrected
candidate and new patch version. Registry-integrity failure is post-hoc and
does not claim rollback of an already published package; the terminal outcome
must state that manual reconciliation is required. Reconciliation is read-only:
operators compare registry `dist.integrity` with the Release tarball SRI and
never retry `npm publish` after the version exists. A candidate whose version
has already been fixed by an immutable tag or GitHub Release and whose packaged
documentation still carries transient pre-release wording is corrected through
a new candidate and patch-version Release; validation is not weakened and an
existing immutable Release is not rewritten. A superseded candidate that was
never tagged or released may be replaced at the same version.
README title and upgrade locators intentionally include fenced examples, so
README examples must not duplicate `# musubix5`, `## Upgrade`, or
`## アップグレード`. CHANGELOG heading scans exclude fenced code because
changelog examples are not release entries.
The documentation validator fail-closes on the closed transient-token list,
including `rc`, `beta`, and `alpha`. Other semantic-version prerelease
identifiers remain excluded by release-process convention rather than by this
documentation check.
