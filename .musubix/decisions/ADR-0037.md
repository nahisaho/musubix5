# ADR-0037: Restart recovery with generation-bound executable authority

## Context

Generation 9 successfully recorded its one native design approval and sealed
RecoveryAuthority29, then stopped between epochs before P, claim or D1. The
approved r29 design did not define five values required for a safe write:
claim lockFence derivation, canonical empty attempt/owner ledgers, the physical
BudgetSpec owner root, claim-journal sequence/predecessor, and the complete
pending/transient write set. Inferring them from diagnostic models would turn
historical examples into authority and could create a non-resumable partial
campaign.

## Decision

Continue CHANGE-0017 as generation 10 with fresh requirements/design approvals
and a new coordinator, DES-M5-024. Preserve every Generation-9 byte and consumed
invocation as immutable non-credit history. Retain authorityKey and pId only as
allocation namespace compatibility values and bind all write authority to
RecoveryAuthority10, the current approvals, a fresh consent event, baseline
HEAD, complete writer inventory and a durable monotonic fence counter.

Use a new `g10-recovery-v1` physical P root. Define exact canonical genesis,
registry, seal, claim-journal and accounting schemas; one claim journal entry
with sequence 1 and null predecessor; a finite final/pending/writing allowlist;
and a total state/observation/action table. Precharge every possible final and
transient byte, keep the total at or below 536870912, and use NoCredit10 and
CreditInvalidation10 so an observed accounting failure cannot later regain
credit. Bind the later native D1 checkpoint to a presealed exact delta rather
than a wildcard path family.

## Rejected alternatives

- Continue Generation 9 and fill the five values from r26/r27 model files:
  rejected because those files explicitly lack executable authority.
- Reuse the Generation-9 approval invocation or consent:
  rejected because the invocation allowance is consumed and generation-bound.
- Use PID/startTicks as `lockFence`:
  rejected because it is not a positive monotonic campaign fence.
- Put BudgetSpec in a session-only or inferred owner root:
  rejected because P verification and accounting require one repository path.
- Allow generic `*.writing` or directory-wide transient paths:
  rejected because an unexpected file could become success-shaped recovery.
- Stop permanently on every post-dispatch error:
  rejected because a bounded release-only path is required to preserve claim
  classification and writer liveness.

## Consequences

The design and implementation are larger because every crash boundary and byte
owner is explicit. Recovery can restart without inventing history, every
partial state has one action, the 512 MiB limit is measurable before writes,
and a failed or ambiguous campaign cannot acquire D1 credit. A new explicit
requirements approval and design approval are required before implementation;
the historical Generation-9 design remains reviewable but non-current.
