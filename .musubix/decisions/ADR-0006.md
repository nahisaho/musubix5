# ADR-0006: Separate baseline, candidate, QA, and bootstrap workspaces

## Context

musubix4 demonstrated that process-local baseline state and reuse of a dirty
real worktree can misclassify user files, contaminate rollback, and retain
rejected candidate changes.

## Decision

Require an immutable baseline commit before candidate execution. Give each
CHANGE a branch or worktree and create a separate QA workspace from the exact
candidate identity. Bootstrap uses its own state root and a restricted
candidate workspace. Expose bootstrap only through explicit musubix5-only
commands `bootstrap run`, `bootstrap resume`, and `bootstrap status`. Track
byte, mode, index, staged, unstaged, deletion, and untracked ownership.

## Rejected alternatives

- Recompute baseline from current HEAD after a run: rejected because run output
  can be absorbed into the baseline.
- Share one mutable worktree among CHANGEs: rejected because ownership and
  evidence isolation cannot be proven.
- Let bootstrap modify the normal workspace directly: rejected because it
  would bypass normal evidence boundaries.

## Consequences

Workspace creation and cleanup require explicit identity checks and safe,
targeted operations. Bootstrap output must re-enter the normal lifecycle.
