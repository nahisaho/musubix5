# ADR-0027: Encode logical candidate identities as portable filesystem keys

Status: accepted

## Context

Candidate と integration の logical identity はそれぞれ
`candidate:<64-lowercase-hex>` と `integration:<64-lowercase-hex>` であり、
journal、evidence binding、CLI、JSON の安定契約として既に使用している。一方、
colon は Windows の directory component に使用できないため、logical ID を
`.musubix/candidates/**` の directory name に直接使用すると state creation と
integration materialization が `ENOENT` で失敗する。

Logical identity を変更すると既存のbinding、journal chronology、candidate gate、
integration IDが変わる。したがってidentity contractを維持したまま、全path builderが
同じportable projectionだけを使用する必要がある。

## Decision

Logical IDとfilesystem keyを分離する単一codecをanalysis packageに置く。
`candidate:<hex>`は`candidate-<same-hex>`、`integration:<hex>`は
`integration-<same-hex>`へprefix substitutionし、逆変換でも同じhexを保持する。
Encoderはexact lowercase 64-hex logical IDだけを受け付け、decoderはexact canonical
keyだけを受け付ける。

Candidate state root、evidence root、report root、integration state root、
materialization source/destination、ownership scanはすべてcodecを経由する。
Registry、journal、evidence binding、diagnostic、CLI/JSONはlogical IDだけを保持し、
machine-local absolute projection rootを永続化しない。Path joinはvalidation後に
state routerだけがplatform-native APIで行い、platform-native absolute rootを返す。
Codecのkeyはbranded typeとし、raw stringをroot builderへ渡せないようにする。
Registered integration worktreeはGit common directory relativeの
`musubix5/workspaces/integrations/<integration-key>`に置き、同じbranded keyなしに
pathを構築できない。Complete relative rootは112文字以下とし、上限超過または
platform path API rejectionはpartial registrationを残さず
`CANDIDATE_STATE_OWNERSHIP`へ正規化する。
要求の95/112文字上限はcandidate/integration owner rootに適用し、その配下の
`evidence/`と`reports/`は別のrelative descendantとして扱う。

Raw logical-ID directory、percent-encoded alias、case variant、reserved name、
symlink alias、その他noncanonical owner memberはlegacy pathとして読まず、
`CANDIDATE_STATE_OWNERSHIP`でfail-closedにする。新規write、materialization、
stage、commitはcanonical keyだけを使用する。Candidate keyは74文字、
integration keyは76文字であり、repository-relative projection rootは要求上限内に
収める。Path APIがrootを拒否した場合も同diagnosticへ正規化し、current operationが
作成したと証明できるpartial directoryだけをcleanupする。

Registry atomic replaceのsame-directory temporary fileは
`registry.json.<pid>-<uuid>.tmp`だけを許可する。これはstate memberではなく、
fingerprint、materialization、stage、commitから除外する。Append lease holderは
live writerが所有しないことを確認したstale tempだけをreclaimできる。Owner-specific
operationは対象componentとancestorだけを検証し、whole-root scanはregistry rebuild、
materialization、stage、commit前に実行する。Read-only inspectionはoffending memberを
列挙するがunknown stateを自動削除しない。

## Alternatives considered

- Logical ID自体をhyphen形式へ変更する案は、journal、binding、CLI出力、
  integration identityを破壊するため却下した。
- `encodeURIComponent`による`%3A`変換はplatform上は有効だが、hex caseや複数の
  equivalent escape表現をcanonical化する追加規則が必要で、owner alias surfaceを
  増やすため却下した。
- Logical ID全体を再hashしてdirectory名にする案はcollision riskを実用上抑えられる
  が、identityとの対応をinspectionだけで確認できず、追加mapping stateが必要なため
  却下した。
- POSIX上のraw colon directoryをlegacy read fallbackとして残す案は、integration
  commitへ混入するとWindows checkout不能になり、platformごとに異なるstate viewを
  作るため却下した。

## Consequences

- Logical evidence identityとfilesystem portabilityを独立に維持できる。
- 全path builderとdirectory scanが単一codecへ依存し、direct joinは禁止される。
- Registry atomic replaceは認識済みoperational temp grammarを使用し、crash残骸を
  append lease下で安全にreclaimできる。
- 未リリースのraw-ID directoryは自動migrationせず、検出時に明示的なownership
  failureとなる。
- Ubuntu、Windows、macOSで同じlogical IDからbyte-exactに同じkeyが得られ、
  committed treeへcolon-bearing candidate state componentが入らない。
