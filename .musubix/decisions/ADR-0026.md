# ADR-0026: Integrate candidates by immutable commits in a clean registered context

Status: proposed

## Context

複数 candidate の branch を default branch 上で順次 merge しながら検証すると、
途中失敗が shared branch を汚染し、再実行時の入力集合と順序が不明確になる。
Path が重ならなくても依存順、base commit、candidate tip、generated operational
state の materialization timing が異なれば統合結果と検証 fingerprint が変わる。

既存 parallel integration は1 CHANGE 内の assignment commit range を扱うが、
複数 CHANGE の approval、quality、candidate gate、release boundary を共有しては
ならない。統合時だけ、選択した候補集合と全履歴を読みながら、credit を候補集合へ
限定する明示 context が必要である。

## Decision

統合開始前に、各 candidate の immutable commit 到達可能性、base、明示依存、
既統合状態、generated operational path を除く変更 path を検証する。同一 path の
ownership overlap、dependency cycle、未完了 dependency、stale base、moved or
unreachable tip は worktree 作成前に拒否する。適格候補は dependency の stable
topological order と candidate ID tie-breaker で並べる。

Integration ID は repository identity、開始 default branch commit、および
candidate ID の byte 昇順に並べた CHANGE ID、generation、candidate ID、
candidate commit を canonical JSON 化して SHA-256 で導出する。Dependency の
stable topological order は commit 適用順だけを決め、identity tuple の順序を
変更しない。統合集合で byte-lowest の CHANGE ID を release owner として別 field
に保存するが integration ID には含めない。同じ ID の再実行だけを resume として
扱い、異なる candidate set は既存 attempt を再利用しない。

Candidate commits は clean な registered integration worktree へ保存済み順序で適用
する。適用後かつ operational state materialization 前の source tree から generated
operational path を除外し、DES-M5-012 と同じ NFC path、Git mode、object type、
object ID、canonical byte order を持つ `integration-source-manifest-v1` を作る。
Configured required commands、
strict trace、graph gate、changed gate、status は CHANGE lease と append lease を
保持せず、integration worktree を source root、control root の candidate state を
read-only evidence root とする明示 integration context で実行し、各 report hash と
入力 commit を verified transition に保存する。

Finalization は全 candidate の CHANGE lease を昇順取得した1つの
`withMultiChangeWrite` transaction 内で state、generation、base、exact input
commit、reachability を再検証し、その callback に渡された repository append
lease session を再取得せず使用する。Verified record append 後に control
operational state fingerprint baseline を取得し、integration worktree への
materialization、integration commit、同じ path set の fingerprint 再照合を行う。
Git subprocess は有限 timeout を持ち、lease renewal は非同期に継続し、各不可逆
step 前に fencing token を再検証する。

Control worktree は operational path 以外が完全に clean で、operational bytes が
integration commit と一致する場合だけ更新対象になる。Default branch は
ref movement 前に Git common directory の untracked
`candidate-finalization-v1` marker へ integration ID、integration commit、
starting default commit、fencing token を保存してから、
`update-ref <default-ref> <integration-commit> <starting-default-commit>` の
compare-and-swap で fast-forward し、同じ fenced transaction 内で branch-owning
control worktree の index と files を integration commit へ refresh する。Ref
movement 後の crash は resume が marker schema と fencing lineage、integration
registry binding、current ref、integration commit reachability の順で照合して
index/worktree refresh と integrated append を idempotent に完了し、marker を
削除する。Ref が開始 commit のままなら pre-CAS abort として marker を削除して
同じ attempt を再試行可能にし、CAS failure、成功、recovery の全 terminal path で
marker を残さない。Operational state drift は何も
更新せず停止するが、default tip advance は入力 candidate を stale にする。Fast-forward 後の
integrated transition は integration commit と materialized candidate-tree manifest
に結合し、integration commit 自身には post-commit record を含めない。Fast-forward
後かつ integrated append 前の crash は、保存済み attempt が結合した integration
commit と現在の default tip または一意に到達可能な commit が一致する場合に限り、
resume が integrated transition を idempotent に補完する。

## Alternatives considered

- Default branch 上で候補を順次 merge して各段階を検証する案は、途中失敗を
  atomic に破棄できず、検証対象 commit が変化するため却下した。
- Git の自動 merge 成功を ownership conflict 解決として扱う案は、同一 path の
  意味的な上書きを success-shaped に受理するため却下した。
- Candidate approval と quality evidence を integration 全体の release credit として
  再利用する案は、候補間相互作用を検証せず release readiness を成立させるため
  却下した。
- Integration ID に時刻や一時 worktree path を含める案は、同じ入力の retry が
  同一 attempt を再開できなくなるため却下した。

## Consequences

- 同じ入力集合、base、dependency graph から同じ integration ID、順序、source
  manifest が得られる。
- Git conflict と semantic conflict の両方に対し、少なくとも path overlap と完全
  verification による fail-closed 境界を持つ。
- Integration verification は候補ごとの証跡を尊重しつつ、統合 tree 上で全必須
  check を再実行する。
- Verified 後でも default tip、candidate commit、control operational state の drift
  は finalization を停止し、古い release approval、candidate gate、attestation は
  stale になる。
- Verification failure または operator abort は integration attempt を terminal
  failure として記録し、binding が変化していない candidate は ready へ戻す。Clean
  integration worktree は明示 cleanup で除去でき、candidate branch と証跡は保持する。
- Integrating または verified candidate を異なる candidate set で再投入すると
  `CANDIDATE_INTEGRATION_CONFLICT` で停止し、既存 attempt を変更しない。
- Integrated transition は release-owner candidate だけの branch、worktree、
  registry tip を verified integration commit へ rebind し、旧 candidate commit を
  journal に保持する。他 candidate ref は変更しない。Owner candidate 上で full-set
  quality、通常の candidate snapshot、candidate gate、domain-less release approval
  を再取得し、tag 時点では owner を sole active CHANGE とする。これにより既存
  release artifact、attestation、authorization schema を増やさない。
