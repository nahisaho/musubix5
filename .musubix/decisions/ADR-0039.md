# ADR-0039: Distribute oversized TDD source blobs with verified Git LFS

## Context

GitHub rejected the Generation-11 candidate's 126,595,440-byte executable Git
blob. Its source path/digest is
`.musubix/evidence/tdd-source/v1/blobs/7fde7b8afa198da66257f42ee2001d874c7355631e6d1579a5fb5ef1f246df4c`.
Those logical bytes are already bound by immutable TDD/source/journal evidence.
Oversized raw objects also remain in unpublished ancestry, so converting only
the current tree cannot make the ref uploadable.

The user explicitly replaced the chunk-store/parentless proposal with Git LFS.
Actual `.gitattributes` currently disables source text conversion but does not
enable LFS. Candidate-gate, release and npm-publish have no `lfs:true` checkout,
and existing source readers/attribute admission do not resolve/permit LFS.
Generations 13 through 18 are immutable non-credit history after, respectively,
an invalid first distribution Red fixture, invalid batch Red-checkpoint
chronology, unchanged post-design authoritative test source, an invalid passing
Red probe followed by a duplicate valid Red, and fixed current LFS attributes
rejecting a retained raw historical object before the first Red, and an
incomplete isolation allow-list breaking the mandatory global build.
The exact nine-ID CHANGE-0017 set requires Generation-19 requirements and design
approval; five IDs carry substantive LFS behavior deltas. The reviewed
Generation-18 test-source marker must then be replaced with the Generation-19
marker before fresh Reds. This is not configuration already performed.

## Decision

Status: Generation-19 Git LFS requirements approved; design approval pending.
Requirements: REQ-M5-LIFECYCLE-006 REQ-M5-COMPAT-013 REQ-M5-RELEASE-002 REQ-M5-RELEASE-003 REQ-M5-RELEASE-004
Design: DES-M5-012 DES-M5-023

The approved requirements artifact retains historical `Proposed`/`not approved`
wording in its reviewed bytes. The Generation-19 native approval record is the
authoritative status; those labels are not an authorization predicate.

Keep the existing blob path and logical SHA-256 identity. Logical files below
100,000,000 decimal bytes stay raw; files at/above the threshold use canonical
three-line Git LFS v1 pointers and complete LFS objects, within the existing
1 GiB logical bound. Use exact measured per-digest attributes, standard
verified Git LFS >=3.4.1, no arbitrary filters or unreviewed endpoint overrides.
DES-M5-023 specifies raw defaults and the exact oversized path's
`filter=lfs diff=lfs merge=lfs -text !eol !working-tree-encoding !ident`.
Check effective global/system/nested/info precedence and candidate-index rules.

Git manifests/approvals still bind exact Git pointer object IDs/bytes; logical
source digests still bind reconstructed bytes. Resolve by immutable entry and
attributes, never by sniffing raw input or trusting hydrated files. Parse the
closed canonical pointer, require OID equal to the path's logical digest and
exact declared size, and independently stream/hash cache/download/worktree
bytes before any use. Preserve original executable modes with atomic verified
materialization; neither pointer-only checkout nor successful smudge is proof.
The original executable must reconstruct exactly its recorded digest and
126,595,440 bytes. Readers and candidate artifact closure need explicit LFS
support; raw Git readers remain raw for pointer-tree/audit correctness.

After renewed approval, inventory oversized digest paths and all published
protected refs, then run scoped Git LFS import on a new isolated local branch.
Preserve published history, normal ancestry and all existing journal/TDD/order/
approval file bytes; only selected source representation, associated attributes
and resulting unpublished Git IDs may change. Retain original local refs/
objects and a verified old-to-new commit map. No broad `--everything`, force
rewrite of default, `--no-rewrite` shortcut, or historical evidence-hash repair.
DES-M5-012 defines exact argument arrays, no-network migration environment,
map/parent/tree validation and durable non-credit replay receipts.

Verify and pin migrated lineage R before old snapshot deletion/adoption.
Use existing protection and same-actor tombstone replay, commit the tombstone
as a normal child, establish current approvals/full-set quality, then create
the new snapshot at ordinary clean HEAD C. The proposed separate-root
immutable-target snapshot extension is withdrawn. Snapshot/gate/release
bindings are new; old records/signatures remain historical, never relabeled.
Pending or divergent migration cannot grant readiness or TDD/lifecycle credit.

All nine Actions checkouts in candidate-gate/release/npm-publish must use
`lfs:true` and complete history; the additional npm detached release-evidence
worktree needs explicit exact-commit fetch/hydration. Candidate-gate keeps
`persist-credentials:false`; use scoped read authentication for any later
fetch without credential-bearing remotes/logs. Verify exact Git pointer tree
and logical byte hashes/modes before and after QA; git status alone is not
sufficient. Release builds and evidence/authorization reads independently
reverify objects. No executable, evidence or packaged payload is replaced
with pointer text.

Scan every reachable Git blob, including historical raw objects, below
100,000,000 bytes. Separately inventory and hash-verify every reachable source
LFS object, including historical pointers. Separately authorized LFS upload
precedes Git ref publication, and an initially empty independent cache fetch/
hash check proves remote availability before Git push. A local hit, dry-run,
upload acknowledgement or Git scan is not enough. Recheck in CI/release;
account quota/per-object limits, tool/auth/network/missing failures are
unavailable, and malformed pointer/cache/worktree/hash/size failures are invalid.
Keep explicit secret-free failure diagnostics and no success-shaped fallback.

Protected default D remains ancestor of R/C. Release evidence E descends
from C and becomes default-reachable by ordinary fast-forward/verified merge;
publish evidence P descends from E and is default-reachable. The lightweight
tag stays at C. Preserve release/npm ancestry, multi-CHANGE integration
freshness and exact approval/authorization/OIDC bindings. Do not reintroduce
unmigrated U through any pushed ref or merge parent.

## Rejected alternatives

- **Chunk store or parentless candidates:** withdrawn at the user's direction;
  Git LFS is now the required distribution mechanism.
- **Increase process `maxBuffer`:** rejected because it fixes local reads but not
  GitHub's server-side object-size rejection.
- **Drop the executable from the source snapshot:** rejected because the runner
  identity and replay closure would become incomplete.
- **Add LFS attributes/convert only the tip:** insufficient because old raw Git
  blobs are still reachable and GitHub rejects them.
- **Rewrite historical evidence/published history:** rejected; only scoped
  unpublished representation/commit IDs may change, with a retained map.
- **Trust pointer text, smudge, local cache or upload acknowledgement:** rejected;
  independently reconstruct and verify logical bytes and remote availability.
- **Delete old snapshot before verified migration retention:** rejected because
  crash recovery would lose replacement authority.

## Consequences

LFS adds a tool/service/authentication/storage dependency and remote quota risks,
but logical evidence hashes remain unchanged. Git IDs of migrated unpublished
commits change, so fresh candidate snapshots/gates/release approval are required.
REQ-M5-LIFECYCLE-006, REQ-M5-COMPAT-013 and REQ-M5-RELEASE-002/003/004
received renewed Generation-19 requirements approval and require design approval
before implementation. TEST-M5-TDD-SOURCE-LFS-001
and TEST-M5-CANDIDATE-GIT-DISTRIBUTION-001 cover threshold, canonical pointers,
logical reconstruction, workflow hydration, local/remote integrity and replay.

Published oversized history or incompatible immutable journal prefixes remain
blocking: this proposal does not rewrite/repair them. The pre-existing staging
authorization bootstrap also remains unresolved—release approval is required
for a push, but GitHub gate evidence first needs C's remote branch. LFS does
not grant upload/staging permission; a compliant authorized QA route or
separately approved scoped staging requirement is still needed.
