# ADR-0041: Treat project config as a shared implementation fingerprint input

Status: Proposed for Generation 27; requirements approved, design approval pending.

## Context

Generation 20 approved changing only `.musubix/config.json`, recorded a genuine
timeout Red, and then could not record Implementation. The lifecycle fingerprint
algorithm hashed traced non-test code only, while the requirement-scoped
projection also contained only Code Graph implementation paths. The approved
config change therefore appeared unchanged to both guards.
Generation 21 implemented the classification but its Green test compared the
missing-config result against a config-present baseline. Generation 22 used the
corrected baseline but its Red failed on a malformed sentinel journal before
reaching the fingerprint assertions. Generation 23 proved the decision but used
an overbroad CHANGE requirement set. Generation 24 retains the valid journal
fixture, narrows the CHANGE to REQ-M5-LIFECYCLE-006, and reaches the corrected
missing-config baseline before adding one readable regular config.
Generation 24 implemented and proved this decision but was abandoned after an
independent timeout-policy digest defect surfaced at quality. Generation 25
retained the implementation but could not checkpoint its test-only correction.
Generation 26 retains the shared fingerprint implementation unchanged and adds
the affected candidate-gate function's approved trace identity.
Generation 26 quality then exposed duplicate current-cycle selection and
parallel-cycle classification work inside one evidence validation invocation.

## Decision

When `.musubix/config.json` is a readable regular file, add it exactly once to
the aggregate implementation path set and every requested requirement's
implementation path set. Sort and deduplicate before the existing snapshot
algorithm records path-keyed content hashes. The existing workspace-state
capture continues to record mode and size for drift detection. Use the same
helper for control-root and workspace-backed calculations.

Use `lstat` and do not follow symbolic links. Control-root calculations read the
config from their project root; workspace-backed calculations read it from
`sourceRoot` while retaining control-root TDD evidence. Missing config retains the legacy
code-only projection. A symbolic link, non-regular entry, or unreadable config
fails before checkpoint persistence with the approved exit-2 message.

Persisted historical fingerprints remain opaque recorded evidence. Replay,
gate, and generation projection do not recompute them under the new algorithm;
only newly requested checkpoints use the new path sets.

For Generation 27, `validateChangeEvidence()` creates one lazy local Promise
Map keyed by CHANGE ID and requirement ID and routes both of its current-cycle
consumers through that Map. The selector itself creates a separate local
classification Map keyed by cycle ID so fallback reuses an authoritative-loop
classification of the same parallel cycle. Both caches are sequential,
invocation-local and discarded on return or rejection. They do not change
selected evidence, persistence, diagnostics, rejection semantics or historical
fingerprints.

## Consequences

An approved config-only change can produce a real Implementation checkpoint.
Because config is shared execution policy, changing it affects every requirement
requested by that fingerprint calculation. TDD, approval, predecessor, and
unchanged-test guards remain independent and prevent the classification from
granting behavior credit by itself.
The validation caches remove duplicate read-only classification work without
creating cross-call state. A deterministic operation ledger proves at-most-once
classification per complete context independently for two validation calls;
wall-clock limits remain secondary quality guards.

## Rejected alternatives

- Add a no-op production edit: rejected because it would falsify the approved
  config-only implementation.
- Waive or bypass the unchanged guard: rejected because no record-time waiver
  exists and success-shaped evidence would be unauditable.
- Follow symlinks: rejected because an external mutable target would escape the
  repository fingerprint boundary.
- Recompute old checkpoints: rejected because append-only historical evidence
  must retain its original algorithm and bytes.
- Use a module-global cache: rejected because roots, evidence and validation
  purpose could cross-contaminate later calls.
- Prove the optimization only with elapsed time: rejected because wall-clock
  duration is nondeterministic and does not prove the operation bound.
