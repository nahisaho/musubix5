# ADR-0008: Extend approval manifests without weakening exact-hash approval

## Context

musubix3 requirements and design manifests do not bind configuration
projections, and its release manifest includes historical files that musubix5
must not treat as active evidence.

## Decision

Keep exact sorted manifests and SHA-256 approval. Add canonical
requirements-policy and execution-policy projections as manifest entries.
Preserve musubix3's base path sets, then apply the explicitly registered
historical, run-local, and foreign-CHANGE release exclusions. Display every
included and excluded path with its reason.

Build the release manifest from an immutable candidate Git tree. Store the
release approval record outside that tree and expose any worktree-local approval
file only as a derived projection, preventing the approval from hashing itself.

Bootstrap approvals produced by musubix3 authorize development only. Native
musubix5 approval of the same normative content set is mandatory before
release. Release approval and external release-operation authorization remain
separate.

## Rejected alternatives

- Treat bootstrap approvals as native release evidence: rejected because the
  producer and manifest semantics differ.
- Hash all generated evidence into every stage: rejected because it creates
  self-reference and unstable approval digests.
- Preserve the v0.1.18 release path set exactly: rejected because historical
  and foreign-CHANGE artifacts would enter the candidate manifest.

## Consequences

Approval hashes intentionally differ from musubix3 where projections or new
release exclusions apply. Migration guidance and regression tests are required.
