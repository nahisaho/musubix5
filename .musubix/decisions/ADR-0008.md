# ADR-0008: Extend approval manifests without weakening exact-hash approval

## Context

musubix3 requirements and design manifests do not bind configuration
projections, and its release manifest includes historical files that musubix5
must not treat as active evidence.

## Decision

Keep exact sorted manifests and SHA-256 approval. Native musubix5 manifests use
`approval-manifest-schema-v1`, canonical effective-configuration projections,
NFC path identities, and explicit domain binding. Pinned-musubix3 bootstrap
approvals remain hash/projection bindings and are not required to emit the
native schema.

Requirements and design manifests resolve the fixed normative path set from the
invoking workspace. Release manifests read blobs from the persisted immutable
candidate commit, never from mutable worktree files. They apply the closed,
first-match exclusion registry in REQ-M5-APPROVAL-007, display raw hashes for
included and excluded blobs, and bind only included hashes plus excluded
path/reason pairs. Both release approval destinations are excluded so native
and compatibility services derive the same aggregate without self-reference.

Reject missing or non-regular normative inputs, invalid path encoding, NFC path
collisions, unavailable candidate commits, and Gitlinks with classified
`APPROVAL_*` diagnostics. Worktree-only mutation cannot change a candidate-tree
release manifest. Included generated projections and attestations must be
committed before selecting the candidate snapshot. The closed nine-rule
exclusion registry is then applied to the snapshot's blobs; gate outputs that
cannot be committed before snapshot selection are limited to the closed
`gate-self-reference` list.

Bootstrap approvals produced by musubix3 authorize development only. Native
musubix5 approval of the same normative content set is mandatory before
release. Release approval and external release-operation authorization remain
separate.

## Rejected alternatives

- Treat bootstrap approvals as native release evidence: rejected because the
  producer and manifest semantics differ.
- Hash all generated evidence into every stage: rejected because it creates
  self-reference and unstable approval digests.
- Build release approval from the mutable worktree: rejected because concurrent
  logs, run-local artifacts, and gate refreshes make an approved hash stale.
- Let each approval producer exclude only its own record: rejected because
  producer identity would change the aggregate for the same candidate.
- Preserve the v0.1.18 release path set exactly: rejected because historical
  and foreign-CHANGE artifacts would enter the candidate manifest.

## Consequences

Approval hashes intentionally differ from musubix3 where projections, schema,
candidate-tree sourcing, diagnostics, or release exclusions apply. Migration
guidance and regression tests are required. A requirements or design manifest
change supersedes downstream approval and evidence through the normal lifecycle.
Changing a declared default changes the effective projection and requires
renewed approval even when the key was previously omitted. Selecting a new
candidate snapshot supersedes an existing release manifest and approval.
