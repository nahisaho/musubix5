# ADR-0010: Version change cycles and bind release gates to candidates

## Context

CHANGE-0002 reached release review with three coupled failures. Workflow
declarations were matched through one global invocation cursor even when
different Skills legitimately completed in a different order. Compatible
reconciliation depended on raw local transcripts that could not be retained
privacy-safely when their terminal lifecycle was non-strict. Release manifests
were built from an immutable candidate while gate results were produced from a
later mutable worktree. Reopening the approved requirements also exposed that
one-shot change phase keys could not represent a second lifecycle cycle.

## Decision

Represent each CHANGE lifecycle attempt as a positive integer generation.
Legacy records are generation 1; new records use generation-qualified order
keys and bind all normal evidence to the active generation. A completed
generation can reopen at impact. An incomplete generation must be explicitly
abandoned before reopening, remains historical, and grants no readiness.
Requirements/design supersession inside an active generation remains the normal
approval cascade.

Reconcile workflow declarations only within the active CHANGE and generation.
Use one invocation cursor per Skill, retain strict terminal proof for at least
one source, and allow additional privacy-minimized compatible sources. Reject
duplicate source digests and event identities.

Derive release gate inputs only from the persisted candidate commit. Execute
the complete musubix5 verification matrix in isolated QA workspaces, compare
tracked blobs before and after each run, and persist the results as external
generation-bound evidence. Cross-platform result artifacts use GitHub OIDC
strict attestation with ephemeral public-key binding and a separate 24-hour
matrix transport freshness window. The release manifest projection binds
repository identity, candidate commit, and the candidate-derived gate input
fingerprint.

Expose candidate persistence as the public `candidate-snapshot
create|list|show|delete` lifecycle. Creation treats its CHANGE argument as
confirmation of the sole implicit active CHANGE, requires current
requirements/design approvals plus full-set quality, and persists a
generation-bound record with stable `snapshot-<12-digit-order>` identity and a
SHA-256 `candidate-tree-manifest-v1`. Candidate commits and every related
approval, gate, release-operation, release-workflow, npm-workflow, TDD, and
parallel-start boundary accept lowercase hexadecimal Git object IDs of length
40 through 64; shorter, longer, uppercase, or non-hexadecimal values are
invalid. Exactly one repository-matching live snapshot is permitted per
CHANGE; replacement requires explicit append-only deletion.

Projection is deterministic across new and legacy records. Legacy records omit
payload `recordVersion`, project nullable generation/digest/time, remain
inspectable and deletable, but are stale and replacement-required. Foreign
records remain visible but do not block local creation. List never fails merely
because history conflicts; show resolves an exact snapshot ID or the sole live
repository-matching CHANGE record. A historical multi-record conflict remains
readable with stale release status, unprotected state, and explicit conflict
recovery guidance.

Deletion never rewrites a creation record or Git object. It appends a
`workspace-candidate-snapshot-deleted` tombstone containing the deleted
record's repository identity, actor/time, approval audit fields, and invalidated
candidate-gate/release state. A current release approval protects its selected
snapshot; replacement first requires generation reopen so that approval becomes
non-current. Protection applies equally to legacy records selected by a valid
historical approval; legacy status is not a deletion bypass. Same-actor
deletion replay returns the original tombstone and a different actor is
rejected.

Keep lifecycle structure and lifecycle evaluation acyclic. The workspace
manager parses creation/tombstone records and owns repository, deletion,
reachability, conflict, and legacy facts. The CLI coordinator supplies
read-only approval and quality evaluators from the approval service and quality
engine; create and delete invoke them again under the CHANGE lease before
append. The workspace manager never imports those services. Public
release/npm workflow adapters use one `resolveReleaseCandidate(root, context)`
adapter over the workspace manager's canonical
`resolveCandidateSnapshot(root, context)` selector.

New release approval selects only the active generation's sole live
repository-matching snapshot. Completed/inactive approval validation uses the
closed historical rule, including the legacy greatest-order exception only
when its commit matches the persisted approval candidate. QA is materialized at
the candidate commit, so the later snapshot-journal commit is outside the
candidate tree. Missing, foreign-only, legacy/non-current, conflicting, and
gate-stale states have distinct recovery paths consumed consistently by status,
parallel readiness, and release-operation validation.

Construct repository identity through the DES-M5-003
`repository-identity-v1` canonicalizer before hashing, using the exact grammar,
ASCII-whitespace definition, and normalization order in REQ-M5-WORKTREE-001.
Repository-aware callers read stored values with
`git config --get-all remote.origin.url`, do not apply `url.*.insteadOf`
rewriting, and use the first value because Git fetch uses the first configured
URL. They always supply the absolute `git rev-parse --show-toplevel` path as the
fallback parameter used when the selected origin is absent or trims to empty.
They discard every raw value immediately after canonicalization and never
include it in evidence, manifests, diagnostics, or wrapped errors.
Preserve every distinction outside the two enumerated cosmetic forms. Persist
and compare only the digest so detached GitHub Actions checkouts and developer
clones agree on trailing slash and `.git` spelling without weakening
foreign-repository rejection or exposing credentials.

## Rejected alternatives

- Keep one global workflow cursor: rejected because nested or overlapping
  Skills can complete in an order different from invocation order.
- Waive the order diagnostic: rejected because active waivers cannot grant
  release readiness.
- Reorder or delete historical declarations: rejected because it would mutate
  evidence rather than reconcile it.
- Run the release gate in the mutable control worktree: rejected because the
  evaluated inputs can differ from the approved candidate.
- Mutate the candidate with post-gate evidence: rejected because the evidence
  would invalidate the commit it claims to verify.
- Hide snapshot persistence behind an internal API: rejected because release
  approval otherwise has no executable public transition from a clean candidate
  commit to the required journal evidence.
- Automatically supersede the greatest-order snapshot: rejected because it
  makes accidental later commits silently replace an approved candidate and
  obscures invalidation history.
- Physically delete snapshot evidence: rejected because release recovery and
  audit require immutable creation and tombstone history.
- Add a force-delete bypass: rejected because current release approval must
  remain a hard protection boundary.
- Require the snapshot journal commit to become the candidate: rejected because
  that would recursively change the commit being identified; the journal is
  post-candidate evidence and must not amend the candidate.
- Create a new CHANGE for every supersession: rejected because a reviewed
  CHANGE needs auditable in-place repair while retaining prior generations.
- Compare raw origin strings: rejected because `actions/checkout` and ordinary
  Git clones can spell the same GitHub HTTPS repository with or without
  trailing `.git`.
- Treat SSH, credentials, host-case changes, forks, or alternate schemes as
  equivalent: rejected because transport-tolerant matching would weaken the
  repository ownership boundary.

## Consequences

Change, approval, TDD, workflow, gate, status, and release JSON gain registered
generation or candidate-binding fields. The CLI gains `--reopen`,
`change generation abandon`, `workflow-sanitize --compatible`, and
the `candidate-snapshot create|list|show|delete` group. Existing
generation-less records remain readable as generation 1 without byte changes.
Release approval hashes change because generation and candidate gate projection
are normative. Candidate matrix execution costs more than a single local gate,
but it removes worktree/candidate ambiguity and makes each approved release
hash reproducible. Existing snapshot identities created from either supported
GitHub HTTPS spelling remain comparable after regeneration because all new
identity surfaces use the same canonical digest; genuinely different origins
continue to invalidate approval and operation authorization. A missing
snapshot now has a distinct diagnostic-derived approval hash and executable
recovery guidance. Snapshot deletion and recreation intentionally invalidate
prior candidate-bound gate, release-manifest, and release-approval state while
preserving auditable history.
