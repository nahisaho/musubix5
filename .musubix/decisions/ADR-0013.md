# ADR-0013: Resolve current CHANGE from document status and persisted ownership

## Context

The prior resolver treated every non-abandoned generation as repository-current.
After CHANGE-0002 completed, creating CHANGE-0003 therefore made approval,
workflow, TDD, gate, and status operations fail with
`CHANGE_GENERATION_MIXED`. Abandoning a completed generation would damage
historical readiness, while globally rebinding declarations could attach one
Skill invocation to the wrong CHANGE.

## Decision

Separate historical generation state from current CHANGE selection. Within a
CHANGE, the greatest non-abandoned generation remains its active generation.
For implicit repository operations, select the sole CHANGE document whose
frontmatter status is `active`; a completed document remains historical and is
not current. Preserve legacy documents without frontmatter as active until
migrated. Select an active document even when its generation is null so status
can report an abandoned interval.

Persist `changeId`, generation, and requirement IDs on every workflow
declaration. Add `workflow-record --change-id` for explicit current ownership;
never fall back when an explicit value is supplied. Reconcile declarations by
their persisted scope and report other-CHANGE declarations without rebinding or
blocking the selected CHANGE.

Keep at most one active CHANGE document for ordinary implicit operations.
`status` remains exit 0 with `ready: false` for mixed authoring state, while
state-changing commands and gate fail. Permit explicitly targeted
`parallel status` and stale cleanup as non-credit maintenance for active,
abandoned, or completed CHANGEs.

## Rejected alternatives

- Abandon completed CHANGE-0002: rejected because it would falsify completed
  historical state to work around resolver ambiguity.
- Select the newest journal order globally: rejected because order does not
  express which CHANGE the repository author intends to work on.
- Infer from the current Git branch: rejected because branches are user-managed,
  detached checkouts are valid, and branch spelling is not a normative identity.
- Rebind unowned workflow declarations to the newest CHANGE: rejected because
  one invocation could satisfy unrelated work.
- Add explicit CHANGE options to every existing command immediately: rejected
  as an unnecessary compatibility expansion; document status resolves ordinary
  current work, with explicit targeting added only where cross-CHANGE history is
  intentionally inspected or declared.

## Consequences

Completed CHANGEs coexist without blocking current approval and quality
operations. Repository authors must keep at most one CHANGE document marked
active for ordinary stateful work. Workflow JSON gains registered explicit
ownership behavior. Legacy CHANGE documents remain usable, but migration to
frontmatter status is recommended for deterministic multi-CHANGE history.
