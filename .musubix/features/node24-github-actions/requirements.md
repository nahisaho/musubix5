# Node.js 24 GitHub Actions requirements

## REQ-M5-CI-001: Standardize GitHub Actions on Node.js 24
Priority: must
Type: non-functional
Pattern: state-driven
Statement: While a repository GitHub Actions job installs Node.js, the system shall configure that job to use Node.js 24 without narrowing the published package runtime range.
Acceptance: Every workflow step whose `uses` value identifies `actions/setup-node@<any ref>` by a case-insensitive owner/repository comparison, including a tag or pinned commit SHA, in `.github/workflows/*.yml` and `.github/workflows/*.yaml` resolves to Node.js major version 24; a missing `node-version` is rejected; an accepted literal scalar has string form exactly `24`; an accepted expression is the complete scalar and matches exactly `${{ matrix.<key> }}`, the referencing job's `strategy.matrix` contains only a literal, non-empty `include` key, the referenced key is present in every include entry, and its resolved value set is exactly `{24}`; operators, functions, concatenation, missing or dynamically generated `matrix.include`, a missing referenced key, `node-version-file`, environment variables, workflow inputs, non-`include` matrix axes, and every other version source not statically resolvable by one of those forms are rejected; the candidate verification matrix contains exactly Ubuntu/24, Windows/24, and macOS/24 once each and contains no Node.js 20 or 22 job; the candidate matrix job declares exactly one `actions/upload-artifact` step, whose name is `candidate-gate-${{ matrix.os }}-node${{ matrix.node }}`, whose path is the single `${{ runner.temp }}/candidate-gate-envelope.json` envelope file, and whose `if-no-files-found` value is `error`, so one uniquely named opaque envelope artifact is emitted per matrix job and the current matrix emits exactly three; release and npm-publish jobs use Node.js 24; `package.json` continues to declare `engines.node` as `>=20`; every CI-version passage in `README.md` and `README-ja.md` describes Node.js 24 on Ubuntu, Windows, and macOS while retaining the Node.js `>=20` package requirement; the candidate-gate lifecycle passages in both README files state that each candidate produces one opaque envelope artifact per matrix job, currently exactly three; an accepted ADR and a `docs/migration-guide.md` intentional-difference entry governed by `REQ-M5-COMPAT-007` record the reduced continuously verified Node.js set without narrowing `engines.node`, and `TEST-M5-CI-NODE24-001` verifies both `REQ-M5-CI-001` and `REQ-M5-COMPAT-007`; the pinned musubix3 baseline inventory entries for `CI compatibility`, `runtime`, and `package runtime range` remain byte-unchanged; and Node.js 20/22 remain supported package runtimes but are deliberately no longer continuously verified by the candidate matrix.

## REQ-M5-CI-002: Keep Unix-socket verification paths portable
Priority: must
Type: non-functional
Pattern: state-driven
Statement: While candidate verification runs on any matrix platform, the system shall provide platform-appropriate Unix-domain-socket copy-failure verification without workflow-level `TMPDIR` environment overrides.
Acceptance: The parallel-runtime partial-copy regression creates a real filesystem Unix-domain socket named `z-overlay-copy-failure.sock` whose directory entry resides inside the fixture repository's `.musubix` tree; on POSIX, the dedicated `tests/fixtures/short-unix-socket.ts` module exports `ShortUnixSocketContext`, `createShortSocketDirectory(base = '/tmp')`, and `withShortUnixSocket(targetDirectory, callback, base = '/tmp')`, where `base` is overridable only as a verification seam and normal callers use `/tmp`; `ShortUnixSocketContext.socketPath` is the bounded alias pathname passed to `listen()`, and `ShortUnixSocketContext.targetSocketPath` is the non-alias pathname inside the caller-supplied target directory; the directory helper creates a new unique mode-0700 directory using `mkdtempSync(join(base, 'm5s-'))` and reports an error naming the supplied base when creation fails; normal callers omit `base`, while the focused test derives a single padding component from its resolved controlled parent so `Buffer.byteLength(join(base, 'm5s-XXXXXX', 'target', 'z-overlay-copy-failure.sock'), 'utf8')` is at least 91 and the component remains at most 255 bytes, then asserts that computed precondition before invoking the helper; the socket helper computes `<directory>/target/z-overlay-copy-failure.sock`, rejects it before creating the `target` directory symbolic link or calling `listen()` when it exceeds 90 UTF-8 bytes with a diagnostic naming the pathname and byte length, removes the unique directory on that rejection, and otherwise creates `target` pointing to the caller-supplied target directory, which is the fixture repository's `.musubix` tree in the partial-copy regression, and passes the bounded pathname to `listen()` so the final socket component is created inside that target directory; the 90-byte bound leaves at least 13 bytes below the 104-byte macOS `sun_path` storage including its terminating NUL; that dedicated module does not import `node:os`, read `os.tmpdir()`, or inspect `TMPDIR`, `TMP`, or `TEMP`; before calling `listen()`, the helper installs an error handler and rejects any bind failure with a diagnostic naming the socket pathname and its UTF-8 byte length instead of hanging or emitting an unhandled server error; `withShortUnixSocket()` owns the server and invokes its callback inside `try/finally`, closing the server only when needed, tolerating a socket entry already removed by server close, and removing only a remaining socket through the non-alias `targetSocketPath` when its server reached `listening`, plus the symbolic link and unique directory, after callback success, callback failure, bind failure, or overlength rejection while preserving and rethrowing the original callback, bind, or length failure unless cleanup is the only failure; a pre-existing non-socket entry at `targetSocketPath` survives bind failure; cleanup removes the symbolic link itself and never traverses it into the target directory; on Windows, `withShortUnixSocket()` rejects before filesystem mutation, the focused test asserts that rejection, and its platform-independent source assertions still run; `CODE-M5-CI-SHORT-SOCKET-001` implements the helpers in a code-only annotation block with `@implements REQ-M5-CI-002` and `@design DES-M5-CI-002` and no `@verifies` token; the candidate workflow's `CODE-M5-CI-NODE24-001` annotation also implements `REQ-M5-CI-002`; `TEST-M5-CI-SHORT-SOCKET-PATH-001` verifies uniqueness, mode, reachable overlength rejection and cleanup, dedicated-module dependency constraint, target-directory placement through the directory alias, handled bind error with preservation of a pre-existing non-socket entry, forced-callback-failure cleanup with propagation of the original callback error, preservation of a target sentinel, the test seam's explicit base-directory setup failure, and Windows rejection; `TEST-M5-CI-DEFAULT-TMPDIR-001` verifies `REQ-M5-CI-002` and that `.github/workflows/candidate-gate.yml` contains no `TMPDIR` assignment in any `env` mapping and no write of `TMPDIR` to `GITHUB_ENV`, on every platform; on POSIX, `TEST-M5-PARALLEL-WORKSPACE-PARTIAL-COPY-001` verifies `REQ-M5-CI-002`, observes a non-zero overlay-copy command exit whose diagnostic includes the `z-overlay-copy-failure.sock` basename, and preserves the workspace marker while using the bounded socket helper, while on Windows it retains the existing early return for the Unix-socket-specific portion; the candidate-gate workflow runs its closed verification matrix with the runner's default temporary-directory environment; and the complete Node.js 24 macOS candidate-gate job passes without a workflow `TMPDIR` override and persists a passing `.musubix/evidence/release/gates/macos-node24.json` envelope for the candidate.

## REQ-M5-CI-003: Validate archived runtime evidence across authorized hosts
Priority: must
Type: non-functional
Pattern: state-driven
Statement: While a clean Node.js 24 candidate runner validates archived TDD runtime evidence, the system shall preserve producer-runtime provenance without treating the producer's absolute executable path as authorization for the validator host.
Acceptance: The archived acknowledgment retains its exact observed executable, argv, selected files, selected test IDs, environment projection, execution binding, command/context/invocation/result hashes, content hashes, and acknowledgment hash as immutable inert provenance; changing any archived executable, argv, environment, binding, hash, selected file, or selected test ID fails validation. An acknowledgment missing any required field, containing an empty required string or array, truncating a required value, or reporting incomplete execution fails with the existing domain diagnostic before it grants evidence credit. Archived validation accepts a producer executable outside the validator's filesystem only when every existing canonical hash and candidate-bound execution-binding check succeeds, and it grants no permission to launch that path. A new execution remains authorized only when the launcher selects the validator's current Node.js 24 `process.execPath` or a readable regular repository-local `.musubix-runtime/bin/node` or `node.exe` whose resolved command, platform, architecture, Node major, invocation, and execution binding match the current request; a non-Node executable, Node major other than 24, altered local runtime, missing authorization, or substituted binary is rejected. `TEST-M5-CI-ARCHIVED-RUNTIME-001` fails against the Generation-27 host-path equality, passes unchanged for the same frozen Red/Green acknowledgments on a clean different host, and rejects every listed archived-tamper, missing/truncated/incomplete acknowledgment, and live-authorization case.

## REQ-M5-CI-004: Reconstruct graph and performance inputs in the candidate matrix
Priority: must
Type: non-functional
Pattern: event-driven
Statement: When a candidate matrix job starts from a fresh immutable checkout, the system shall generate and validate every Code Graph and deterministic performance input from that checkout before any consumer uses it.
Acceptance: The job begins without authority from committed or ignored `.musubix/cache/**` files, generates the required graph cache and structured command reports from the checked-out candidate, and verifies them against the candidate's committed requirements, design, trace, source, tests, configuration, and trusted quality policy before use. Each performance observation binds the repository identity, candidate commit, matrix operating system, Node major, command name, canonical command fingerprint, run identity, structured report path and digest, authoritative test identity, deterministic counter, unchanged maximum, and exit status. Reports from another candidate, platform, Node major, command, run, path, digest, test, counter, maximum, or non-passing exit are rejected; matrix mode neither reuses local quality-report paths nor skips required current-run performance generation. `TEST-M5-CI-MATRIX-GRAPH-001` begins without `.musubix/cache/codegraph.json` and `.musubix/cache/test-results/codegraph.json`, proves cache-independent graph ownership and current matrix-scoped performance provenance, rejects every listed mismatch, and preserves the approved deterministic counter maxima on Ubuntu, Windows, and macOS.

## REQ-M5-CI-005: Publish source artifacts with platform-specific durability
Priority: must
Type: non-functional
Pattern: state-driven
Statement: While immutable source artifacts are published on a supported matrix platform, the system shall preserve file durability and fail-closed publication while tolerating only the platform's explicitly unsupported directory-sync operations.
Acceptance: Every platform requires successful source-file write and flush, exclusive no-replace publication, authorization, post-publication size and SHA-256 rehash, and cleanup; none of those failures is suppressible. POSIX requires directory open and `fsync` success except the closed unsupported-sync codes `EINVAL`, `ENOTSUP`, `EISDIR`, and `EBADF`. On Windows only, `EISDIR`, `EPERM`, `EINVAL`, `ENOTSUP`, or `EBADF` raised by opening or syncing the already-published parent directory is treated as unsupported directory sync after all mandatory file-level operations succeed; every other code, every error from another operation, and every authorization, rename, collision, file-flush, size, or hash failure remains `TDD_SOURCE_IO_FAILED` or its existing more-specific fail-closed diagnostic. `TEST-M5-CI-WINDOWS-DURABILITY-001` executes real publication on Windows and injected operation-specific failures on every platform, asserts both closed code sets exactly, proves that `EPERM` remains a failure on POSIX, proves success only for the closed Windows directory-sync set, and proves that all non-directory or non-listed failures retain their original diagnostics.

## REQ-M5-CI-006: Compare candidate trees deterministically across platforms
Priority: must
Type: non-functional
Pattern: state-driven
Statement: While a candidate or QA workspace is materialized on any required matrix platform, the system shall compare its deterministic checkout and verified logical LFS content with the immutable Git candidate without accepting platform conversion or unrelated tracked changes.
Acceptance: Candidate and QA checkout explicitly disable line-ending conversion with `core.autocrlf=false` and preserve LF bytes through repository attributes. Git index entry path, object ID, and mode remain authoritative on every platform; POSIX additionally verifies supported worktree executable bits, while Windows with `core.fileMode=false` does not infer a mode mismatch from unsupported worktree mode bits and still rejects an index-mode mismatch. Exact non-LFS blob bytes hash to the candidate object ID; exact LFS pointer identity, logical size, SHA-256, and allowed Git mode are verified before and after gate execution. Hydration alone does not dirty or invalidate the candidate, while hydration combined with any unrelated tracked byte, index mode, path, object, symlink, or Gitlink change fails with `RELEASE_CANDIDATE_TREE_MISMATCH`. `TEST-M5-CI-WINDOWS-TREE-001` covers LF ordinary blobs and hydrated LFS blobs on Windows, a Windows index-mode mismatch, POSIX worktree executable-bit mismatch, content conversion, and an unrelated tracked mutation after successful hydration.

## REQ-M5-CI-007: Use portable candidate verification fixture names
Priority: must
Type: non-functional
Pattern: ubiquitous
Statement: The system shall use only fixture path components valid and collision-free on Ubuntu, Windows, and macOS.
Acceptance: Portable fixture components contain no control character or Windows-reserved character `<`, `>`, `:`, `"`, `|`, `?`, or `*`, do not end in a dot or space, are not case-insensitively equal to `CON`, `PRN`, `AUX`, `NUL`, `COM1` through `COM9`, or `LPT1` through `LPT9`, are NFC-normalized, remain unique under case-insensitive NFC comparison, are at most 120 UTF-8 bytes each, and keep the resolved fixture path below 240 UTF-8 bytes. `TEST-M5-CI-WINDOWS-FILENAME-001` replaces the newline-containing large-tree component with one satisfying this predicate, creates exactly 7,001 archive entries, preserves Unicode and whitespace coverage through a valid component, proves the raw `git ls-tree -r -z` output remains greater than 1,000,000 bytes and fully ordered, and separately verifies rejection fixtures for every invalid-name class without attempting to create them on an incompatible host.

## REQ-M5-CI-008: Preserve structured candidate workflow failures
Priority: must
Type: functional
Pattern: unwanted-behavior
Statement: If candidate gate execution cannot produce a valid normal gate report, then the system shall emit a bounded structured terminal failure that preserves the primary diagnostic.
Acceptance: The candidate workflow accepts a normal report only when the parsed root is a non-array object, `checks` is an array, and each consumed check has the required typed fields; required non-approval check failures still produce a failing candidate result. The closed abnormal set is runner-module import failure, runner-wrapper startup failure, candidate precondition domain failure, CLI `{error}` envelope, non-object root, missing `checks`, non-array `checks`, invalid check entry, malformed JSON, empty stdout, non-zero subprocess exit, timeout, stream-cap termination, signal termination, and incomplete runtime acknowledgment. Candidate precondition domain failure means a typed failure from candidate commit, repository identity, LFS closure, or tracked-tree verification before the gate subprocess starts; a domain error returned by the subprocess is a CLI `{error}` envelope, not a precondition failure. Incomplete runtime acknowledgment additionally matches a CLI `{error}` envelope whose code is exactly `TEST_RUNTIME_BOOTSTRAP_INVALID` and whose unredacted parsed message contains at least one of the exact substrings `acknowledgment-binding: incomplete command`, `acknowledgment-binding: missing final acknowledgment`, `acknowledgment-binding: truncated acknowledgment`, `acknowledgment-binding: incomplete native inventory`, or `acknowledgment-binding: acknowledgment mismatch`; cause detection occurs before emitted fields are redacted, multiple matches still add the incomplete-acknowledgment cause once, and another message under that code remains only a CLI `{error}` cause. When causes overlap, primary-cause precedence is import/startup failure, candidate precondition domain failure, timeout, stream-cap termination, signal, empty stdout, malformed JSON, non-object root, CLI `{error}`, missing `checks`, non-array `checks`, invalid check entry, non-zero exit, incomplete runtime acknowledgment, then valid normal report; the result also lists every matched abnormal cause in that same order, so an incomplete acknowledgment delivered in an error envelope has CLI `{error}` as primary and also lists incomplete acknowledgment. Each abnormal case exits the matrix job non-zero and produces `status: fail`, error code `CANDIDATE_GATE_REPORT_INVALID`, `originalDomainCode: null` and `originalDomainMessage: null` when no domain error exists, otherwise the redacted original domain code and message, subprocess exit/signal/timeout identity, `drainTruncated`, SHA-256 of every unredacted raw stdout and stderr byte read until the corresponding pipe closes or until a 5,000-millisecond drain deadline after any normal or abnormal subprocess exit, and at most the final 20,000 Unicode scalar values of each stream. Each stdout and stderr raw spool has an independent 100,000,000-byte retention cap; the first byte beyond a cap triggers stream-cap termination, is not retained in the raw spool, but it and later bytes observed during the bounded drain still contribute to that stream's SHA-256 and redacted diagnostic tail. The gate subprocess timeout is the selected command's configured positive timeout and must not exceed 300,000 milliseconds. On timeout or stream-cap termination the runner first performs platform-appropriate process-tree termination. When the drain deadline expires after any exit the runner closes its readers, records `drainTruncated: true`, and hashes exactly the bytes observed before closure; otherwise it records `false`. The raw digests are intentionally retained as one-way integrity bindings and never expose stream contents. Streams are decoded as UTF-8 with invalid sequences replaced by U+FFFD. The closed GitHub-token pattern is `(?:gh[pousr]_[A-Za-z0-9]{20,255}|github_pat_[A-Za-z0-9_]{20,255})`. An authorization header is a case-insensitive substring matching `Authorization\"?[ \t]*:[ \t]*[^\r\n]+`; the complete value after the colon is replaced while the header name and optional closing quote remain, including deliberate over-redaction through closing JSON syntax on that logical line. Configured-secret representations in scope are the exact raw value, its JSON string-escaped form without surrounding quotes, and those forms with ANSI control sequences interleaved; URL encoding, base64 and every other undeclared transform are outside the claim. Those representations, the closed token pattern, authorization-header values, and every non-empty environment value whose name is `GITHUB_TOKEN`, `GH_TOKEN`, `ACTIONS_ID_TOKEN_REQUEST_TOKEN`, or ends in `_TOKEN`, `_SECRET`, `_PASSWORD`, or `_KEY` are replaced with `[REDACTED]` by a bounded streaming redactor before the final-tail ring is selected, including matches crossing chunk and retained-tail boundaries. No minimum secret length is applied; over-redaction is preferred to disclosure, and overlapping configured values are matched longest first. Import, startup, or candidate precondition failure before subprocess creation uses null exit and signal, `timedOut: false`, `drainTruncated: false`, and the SHA-256 of an empty byte stream for each stream; import/startup preserves `GATE_RUNNER_UNAVAILABLE`, while precondition failure preserves its typed domain code and message. A non-zero exit or incomplete runtime acknowledgment remains abnormal and cannot be converted to `status: pass` even when parsed required checks otherwise pass; available redacted check diagnostics are retained. No abnormal case produces or uploads an envelope with `status: pass`. A failing envelope may be signed and uploaded for diagnosis but cannot satisfy candidate-gate ingestion or REQ-M5-RELEASE-002. `TEST-M5-CI-MATRIX-ERROR-001` independently exercises the normal-pass report, normal report with a failed required check, and every member and overlap precedence of the closed abnormal set, including non-zero exit with otherwise-passing checks and incomplete runtime acknowledgment, and proves the workflow never dereferences an unvalidated property, loses a matched cause, leaks an in-scope secret representation, or hides the primary diagnostic.
