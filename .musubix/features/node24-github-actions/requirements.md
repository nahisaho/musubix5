# Node.js 24 GitHub Actions requirements

Generation-50-Review-Delta: Generation 50 retains the Generation 49 candidate
source, approved workflow limits, and one-envelope-per-matrix-job transport,
but supersedes its release candidacy after the immutable candidate failed the
required Ubuntu, Windows, and macOS Node.js 24 matrix twice. The following
paragraph is a Generation-50 acceptance extension of REQ-M5-CI-008 and is
verified by `TEST-M5-CI-MATRIX-FAILED-TEST-DIAG-001` for failed-test
enrichment and `TEST-M5-CI-INCOMPLETE-COMMAND-DIAG-001` for incomplete-command
enrichment.

In the normal-report processing path, when a required command fails and its
current matrix-run structured adapter report passes the REQ-M5-CI-004
repository, candidate commit, platform, Node major, run ID, command fingerprint,
report-path, report-digest, and exit provenance checks, the system shall add
bounded informational failed-test diagnostics to that command's existing
`checks[].diagnostics` array before the candidate runner sanitizes the check.
The report must be a non-symbolic regular file no larger than 4,000,000 bytes
under the current matrix-run command directory. For the configured Vitest
adapter, `testResults[].assertionResults[]` recognizes only `passed`, `failed`,
`pending`, `skipped`, `todo`, and `disabled`; only entries whose status is
`failed` are consumed and the other recognized statuses are ignored. Every consumed
entry must expose `fullName` or `title` containing exactly one string ID matching
`^TEST-[A-Z0-9][A-Z0-9-]{0,122}$`, a string `title`, an array
`failureMessages` containing only strings, and a nonnegative traversal index
derived from array order. Failure strings are joined with LF; an empty array is
an empty native message. An assertion entry with any other status, or a failed
entry with a missing, duplicate, overlength, or malformed ID or field, a foreign
or path-escaping report, or a binding or digest mismatch invalidates the
complete enrichment source. An invalid or unreadable enrichment source emits no failed-test
diagnostics and never changes the original command output, failure cause, or
status.

Valid failed tests have unique IDs and are sorted by UTF-8 byte order of test
ID. At most 100 diagnostic entries are emitted per command. If more than 100
tests failed, entries 1 through 99 describe the first 99 sorted failures and
entry 100 uses code
`CANDIDATE_COMMAND_TESTS_OMITTED` to report the exact omitted count; otherwise
every entry uses code `CANDIDATE_COMMAND_TEST_FAILED`. Each entry has severity
`error`. Its optional path is emitted only when the report path is a safe
repo-relative POSIX-normalized path with no empty, dot, dot-dot, drive, or
absolute component and redaction leaves it unchanged; otherwise the path field
is omitted without invalidating the report. The closed configured command name
and validated test ID form an identity prefix of at most 200 Unicode scalar
values and are never truncated. If the existing secret redactor would change
that command or ID, the complete enrichment source is invalid. The redactor is
then applied independently to the test title and native failure message; a
redactor carry-safety failure invokes the existing result-wide
`tailsDropped: true` and `resultTextDropped: true` behavior, which may remove
original command tails as well as enrichment text and emits no partial
diagnostic. The redacted title retains at most its first 500 Unicode scalar
values including a final `[TRUNCATED]` marker, and the redacted native message
retains at most its final 1,000 Unicode scalar values including an initial
`[TRUNCATED]` marker. A `[REDACTED]` marker intersecting a truncation boundary
is removed as a whole before the applicable `[TRUNCATED]` marker is added.
Fixed labels plus the identity prefix contain at most 300 Unicode scalar values,
so the composed message that names command, test ID, bounded title, and bounded
native message is at most 1,800 Unicode scalar values.

Commands are processed in the closed configured order. First, each command's
sorted failure list is reduced to its at-most-100-entry form above. Then entries
are emitted while the sum of all emitted diagnostic-message scalar counts,
including omission messages, remains at most 200,000. Before the first entry
that would exceed the envelope-wide cap, processing stops for all commands and,
when its bounded message fits, emits one final
`CANDIDATE_COMMAND_TESTS_OMITTED` entry on the current command naming the exact
number of not-emitted diagnostic entries from the current and all later
commands; otherwise it emits no partial entry. No later command receives
another omission entry. Serialization or enrichment-internal failure drops all
enrichment diagnostics and retains the original failed candidate result. These
diagnostics remain inside the single signed envelope required by
REQ-M5-CI-001, are informational, are not inputs to pass computation or
candidate-gate acceptance, and create no additional workflow artifact.

When acknowledgment validation reaches the existing incomplete-command branch,
its unredacted message begins with the exact substring
`acknowledgment-binding: incomplete command`, preserving the existing
REQ-M5-CI-008 cause classification. It appends only trusted runner-observed
fields from the per-command `ProcessResult`, never values copied from an invalid
acknowledgment:
` command=<name>` when the name is one of the seven closed required commands,
` status=<status>` when status is one of `completed`, `missing`, `timeout`, or
`error`, ` exitCode=<integer|null>` when the exit value is null or a safe integer
and null is rendered as the literal `null`,
and ` durationMs=<integer>` when duration is a nonnegative safe integer.
Invalid or unavailable fields are omitted independently. Redaction precedes
the existing 20,000-scalar domain-message bound. The command name comes only
from the runner's closed configured command identity associated with the
`ProcessResult` being processed, never from the acknowledgment. If that result
is unavailable or its name is not one of the seven closed commands,
` command=` is omitted; every other field is still appended independently when
valid. The generic prefix alone is emitted only when no field is valid.
CLI-error remains the primary overlapping cause and incomplete runtime
acknowledgment remains listed once. Neither failed-test enrichment nor
incomplete-command enrichment can convert a failed command, invalid
acknowledgment, or candidate envelope to pass.

## REQ-M5-CI-008: Preserve structured candidate workflow failures
Priority: must
Type: functional
Pattern: unwanted-behavior
Statement: If candidate gate execution cannot produce a valid normal gate report, then the system shall emit a bounded structured terminal failure that preserves the primary diagnostic.
Acceptance: The candidate workflow accepts a normal report only when the parsed root is a non-array object, `checks` is an array, and each consumed check has the required typed fields; required non-approval check failures still produce a failing candidate result. The closed abnormal set is runner-module import failure, runner-wrapper startup failure, candidate precondition domain failure, post-spawn child-process error, runner-processing failure, CLI `{error}` envelope, non-object root, missing `checks`, non-array `checks`, invalid check entry, malformed JSON, empty stdout, non-zero subprocess exit, timeout, stream-cap termination, signal termination, and incomplete runtime acknowledgment. Candidate precondition domain failure means any value thrown while evaluating candidate commit, repository identity, LFS closure, or tracked-tree verification before the gate subprocess starts; a domain error returned by the subprocess is a CLI `{error}` envelope, not a precondition failure. `runCandidateGateWorkflow()` catches every value thrown while evaluating those preconditions. It reads `code` and `message` only through guarded property access that cannot escape the normalizer. When both guarded reads succeed, `code` is a string matching `^[A-Z][A-Z0-9_]{0,127}$`, does not start with `GATE_`, and is not `CANDIDATE_GATE_REPORT_INVALID`, and `message` is a string, the code and the final at most 20,000 Unicode scalar values of the redacted message are preserved; every other thrown value or property-read failure, including null, undefined, a symbol, a throwing getter, a hostile proxy, or a `CandidateGateStartupError`, becomes `CANDIDATE_GATE_PRECONDITION_FAILED` with fixed redacted message `Candidate gate precondition failed.`. No precondition throw escapes as a wrapper-startup failure. Incomplete runtime acknowledgment additionally matches a CLI `{error}` envelope whose code is exactly `TEST_RUNTIME_BOOTSTRAP_INVALID` and whose unredacted parsed message contains at least one of the exact substrings `acknowledgment-binding: incomplete command`, `acknowledgment-binding: missing final acknowledgment`, `acknowledgment-binding: truncated acknowledgment`, `acknowledgment-binding: incomplete native inventory`, or `acknowledgment-binding: acknowledgment mismatch`; cause detection occurs before emitted fields are redacted, multiple matches still add the incomplete-acknowledgment cause once, and another message under that code remains only a CLI `{error}` cause. When causes overlap, primary-cause precedence is import/startup failure, candidate precondition domain failure, post-spawn child-process error, runner-processing failure, timeout, stream-cap termination, signal, empty stdout, malformed JSON, non-object root, CLI `{error}`, missing `checks`, non-array `checks`, invalid check entry, non-zero exit, incomplete runtime acknowledgment, then valid normal report; the result also lists every matched abnormal cause in that same order, so an incomplete acknowledgment delivered in an error envelope has CLI `{error}` as primary and also lists incomplete acknowledgment. Each abnormal case exits the matrix job non-zero and produces `status: fail`, error code `CANDIDATE_GATE_REPORT_INVALID`, `originalDomainCode: null` and `originalDomainMessage: null` when no domain error exists, otherwise the redacted original domain code and message, a nullable redacted `childErrorMessage`, subprocess exit/signal/timeout identity, `drainTruncated`, SHA-256 of every unredacted raw stdout and stderr byte read until the corresponding pipe closes or until a 5,000-millisecond drain deadline after any normal or abnormal subprocess exit, and at most the final 20,000 Unicode scalar values of each stream. Each stdout and stderr raw spool has an independent 100,000,000-byte retention cap; the first byte beyond a cap triggers stream-cap termination, is not retained in the raw spool, but it and later bytes observed during the bounded drain still contribute to that stream's SHA-256 and redacted diagnostic tail. Every configured command executed inside the matrix gate retains its own positive timeout; the closed command `test` may not exceed 900,000 milliseconds, and each other closed command may not exceed 300,000 milliseconds. The outer gate-orchestration timeout is a distinct deterministic budget equal to 75,000 milliseconds plus the sum of the positive configured timeouts for the closed required command set `typecheck`, `build`, `test`, `codegraph-tests`, `compatibility`, `pack-check`, and `pack-smoke`, plus the configured positive `formal.timeoutMs`. The fixed 75,000-millisecond margin is a deterministic engineering allowance for solver discovery, process-runner kill fallbacks, inner-gate Git probes, orchestration startup, matrix input materialization, and other non-command work; candidate precondition probes are outside this outer budget; it does not claim that every possible internal timeout can be exhausted sequentially without the outer timeout firing. Outer process-tree termination and the 5,000-millisecond pipe drain remain separately bounded after outer timeout detection. The command declarations must contain exactly the seven closed required names with no additional command. A missing or duplicate command, a non-integer or non-positive command timeout, a `test` timeout over 900,000 milliseconds, or another command timeout over 300,000 milliseconds, or a `formal.timeoutMs` that is missing, not an integer, or outside 100 through 300,000 milliseconds stops before subprocess creation as a runner-startup failure. After those input checks, the computed outer budget must defensively be asserted as a safe integer from 75,107 through 3,075,000 milliseconds inclusive; violation of that internal invariant also stops before subprocess creation as a runner-startup failure. Wrapper context/config validation, the calculator, the defensive range guard, an `onCommandStart` callback failure, synchronous spawn failure, and a child-process error before the spawn event are converted to the `CandidateGateStartupError` exported by the same built runner module, with stable code `GATE_RUNNER_UNAVAILABLE`; the workflow recognizes startup class with both `instanceof runner.CandidateGateStartupError` and that exact code only for errors thrown before `runCandidateGateWorkflow()` is called. Execution order is runner import, wrapper context/config validation, timeout calculation, candidate/repository/LFS/tree preconditions under one aggregate 300,000-millisecond deadline, secure spool creation, `onCommandStart` immediately before the spawn attempt, then subprocess spawn. Expiry of the aggregate precondition deadline terminates every in-flight probe process tree, waits at most 5,000 milliseconds for bounded cleanup, emits the precondition-domain cause with original code `CANDIDATE_GATE_PRECONDITION_TIMEOUT` and fixed redacted message `Candidate gate precondition timed out.`, uses null exit and signal, `timedOut: false`, `drainTruncated: false`, empty-stream SHA-256 values, and never invokes `onCommandStart` or spawn; it is not the outer `timeout` cause. The outer orchestration timer starts immediately before the spawn attempt and therefore excludes wrapper validation, timeout calculation, preconditions, and spool creation. An import, wrapper-validation, calculator, or defensive-range startup failure occurs before and short-circuits precondition evaluation, so a configured precondition fault is not invoked or listed. A precondition fault occurs before `onCommandStart` and spawn, so it suppresses any later callback, synchronous-spawn, or pre-spawn child-error fault and only the precondition cause is listed; startup and precondition causes therefore never coexist in one result. A precondition fault alone is always normalized as the precondition-domain cause. Secure spool creation failure is converted to `CandidateGateStartupError` in the same runner-command startup `try` region as `onCommandStart`, synchronous spawn, and pre-spawn child errors. Every startup fault after spool creation begins, including partial spool creation failure, `onCommandStart` failure, synchronous spawn failure, and pre-spawn child error, closes opened handles, removes partial and complete spool files/directories, and finishes any child drain within 5,000 milliseconds before returning the startup result. A child-process `error` emitted before the spawn event causes `runCandidateGateCommand()` to cancel the outer timer, terminate a process tree if a PID exists, bound pipe drainage and cleanup, then throw `CandidateGateStartupError`; it never returns a pre-spawn child error as outcome data. A child-process `error` emitted after the spawn event is returned as outcome data with stable original domain code `GATE_SUBPROCESS_ERROR`, nullable redacted `childErrorMessage` limited to the final 20,000 Unicode scalar values, and non-startup structured failure handling. Any other runner-owned exception after spawn and before final result persistence, including stream pumping, hashing, decoding, redaction, or normalization failure, becomes runner-processing failure with stable original domain code `GATE_RUNNER_PROCESSING_FAILED`, a fixed redacted message `Candidate gate runner processing failed.`, and no exception escape. The outer budget must not be replaced by any one command's timeout, and an otherwise valid gate whose aggregate duration exceeds 300,000 milliseconds but remains within that outer budget must not be classified as timeout. Expiry of the outer budget remains the existing structured timeout abnormal case. After the subprocess and bounded drain complete, repeated LFS-closure and tracked-tree verification share one aggregate 300,000-millisecond post-condition deadline. Expiry or another exception in that region terminates every in-flight probe process tree, waits at most 5,000 milliseconds for cleanup, emits runner-processing failure with original code `GATE_RUNNER_PROCESSING_FAILED` and fixed message `Candidate gate runner processing failed.`, retains the subprocess exit/signal/timeout/digest metadata, sets `postTreeMatchesCandidate: false`, and is not the outer `timeout` cause.
