# Candidate gate efficiency requirements

## Scope

These requirements improve the Node.js 24 candidate matrix without weakening
its existing quality, trace, TDD, performance, candidate-tree, Git LFS,
attestation, approval, or fail-closed verification obligations. Generation 50
and GitHub Actions run `37257023320` remain immutable diagnostic inputs and
grant no passing evidence to this change.

## REQ-M5-CI-EFFICIENCY-001: Execute each candidate attempt through a deterministic resource plan
Priority: must
Type: non-functional
Pattern: state-driven
Statement: While a candidate matrix job executes the closed verification command set, the system shall assign each command's declared test corpus to deterministic resource partitions and execute that command-owned corpus exactly once without automatic retries.
Acceptance: The candidate execution plan is a versioned file committed in the candidate tree; its canonical digest is an input to, and therefore is computed before, the gate-input fingerprint, so it is never derived from that fingerprint. The plan declares the complete seven-command order, every command's test selection, resource partition, worker-pool policy, maximum concurrency, and execution-slot budget. A command's authoritative test set is the unique `TEST-*` identities selected by that command's approved configured discovery and explicit selectors after deterministic platform applicability rules; every member appears exactly once within that owning command's effective attempt plan, while an identity intentionally owned by more than one closed command is executed once in each owning command and is not treated as a duplicate across commands. Each of the seven top-level commands is invoked exactly once. Partitions are internal to their owning top-level command. Every runner-direct child launch reserves one execution slot; every Vitest or Node worker pool reserves its declared `maxWorkers` slots; and every test-owned subprocess fanout uses a repository-owned counted launcher that reserves the requested slots before spawn and releases them after bounded termination. Direct use of `spawn`, `fork`, `exec`, or equivalent process creation inside an authoritative test is rejected unless it is the counted launcher implementation itself. The plan's maximum simultaneously reserved slots is the deterministic `candidatePlannedExecutionSlots` counter, and runtime observations must not exceed the declared per-partition worker or fanout limits. Resource-intensive Git LFS boundary, nested-worker, and real-concurrency tests execute in explicitly bounded partitions rather than competing with unrestricted full-suite workers. The runner rejects an unknown partition, overlapping ownership within one command, an unplanned test, a missing authoritative test, a changed plan digest, a retry count above zero, a top-level command invocation count other than seven, an uncounted process-creation call site, or an observed reservation above the declared bound. Command exit, structured-report, TDD, performance, trace, and test-identity provenance remain bound to the original closed command identity; and `TEST-M5-CI-RESOURCE-PLAN-001` verifies complete per-command selection, intentional cross-command ownership, deterministic ordering, bounded high-resource concurrency, top-level invocation count, counted launcher enforcement, worker-slot accounting, zero retries, digest direction, and rejection of every listed mismatch.

## REQ-M5-CI-EFFICIENCY-002: Keep candidate fixtures and runtime bindings portable
Priority: must
Type: functional
Pattern: state-driven
Statement: While candidate verification is running, the system shall construct temporary paths, module references, process bindings, Git LFS observations, and concurrency fixtures using the active platform's canonical semantics.
Acceptance: Candidate tests and runtime launchers do not assume `/tmp`, POSIX root syntax, slash-only absolute paths, executable-bit support, or raw filesystem paths where Node.js requires file URLs; temporary roots derive from an authorized runner or fixture root and are created before use; JavaScript module subprocess arguments use canonical file URLs and round-trip through `fileURLToPath` where a filesystem path is required; absolute-path validation accepts canonical Windows drive and UNC forms only on Windows and canonical POSIX forms only on POSIX, rejects traversal and mixed-form substitutions, and compares paths using the platform's documented case and separator rules; runtime acknowledgment and augmentation bindings canonicalize executable, argv, selected-file, and report paths consistently between producer and validator without weakening their hashes; the existing 99,999,999-, 100,000,000-, and 100,000,001-byte Git LFS boundaries, pointer grammar, cache-integrity check, logical SHA-256 identity, and required source mode remain unchanged, while platform-specific worktree representation is never substituted for those logical obligations; existing deterministic performance counters and maxima remain unchanged, and real concurrency tests continue to prove the same declared operations and state transitions without treating hosted-runner elapsed time as their deterministic counter; and `TEST-M5-CI-PORTABLE-EXECUTION-001` executes the same fixture contract on Ubuntu, Windows, and macOS and covers POSIX paths, drive paths, UNC paths, spaces, non-ASCII characters, file URLs, missing temporary roots, binding tampering, logical LFS identity, unchanged LFS boundaries, and unchanged operation budgets.

Priority: must
Type: non-functional
Pattern: event-driven
Statement: When candidate timeout calibration is requested, the system shall measure one no-retry three-operating-system command shape without granting candidate, stability, or release credit.
Acceptance: This requirement is authoritative over REQ-M5-CI-EFFICIENCY-003 for calibration semantics if duplicated text conflicts. Accepted calibration requires every command, formal check, precondition, post-condition, report, acknowledgment, and persistence operation to finish successfully and uncensored; any nonzero exit, timeout, deadline truncation, runner loss, missing report, incomplete acknowledgment, missing region, Jobs API bootstrap maximum above 40,000 milliseconds, or Jobs API preparation maximum above 80,000 milliseconds rejects the calibration. ## REQ-M5-CI-EFFICIENCY-004: Preserve first-attempt actionable failure evidence
Priority: must
Type: functional
Pattern: unwanted-behavior
Statement: If a candidate command or runtime partition fails, then the system shall preserve a bounded, redacted failure ledger in that attempt's single signed envelope without rerunning the failed work.
Acceptance: The ledger reuses REQ-M5-CI-008's existing `checks[].diagnostics`; it is not a parallel field and remains subject to the existing at-most-100 entries per command and 200,000-scalar envelope-wide diagnostic-message cap. Every failed entry binds the closed command, resource partition, platform, Node major, process status, exit code or signal, elapsed duration, structured-report path and digest when available, and the affected test ID and title when a valid current-run adapter report identifies them. A nested worker failure additionally names its worker pool and bootstrap stage, and a portability failure names the rejected path category without exposing an unredacted absolute private path. Within REQ-M5-CI-008's existing at-most-1,000-scalar native-message limit, a message of 1,000 scalars or fewer is retained completely; a longer message retains its first 400 scalars, one marker of the form `[TRUNCATED middleScalars=<nonnegative integer>]`, and as many final scalars as fit the same 1,000-scalar limit, so the beginning contains the primary assertion or domain error and the end contains terminal stack context. Existing 500-scalar title and 1,800-scalar composed-message limits remain unchanged. When no valid structured report exists, the ledger records the earliest trusted runner-observed lifecycle stage and acknowledgment or augmentation validation cause. Invalid, foreign, oversized, symbolic, stale, digest-mismatched, or redaction-unsafe diagnostic sources add no untrusted fields and cannot change pass computation. The complete ledger remains within the existing single-envelope size and redaction limits, creates no additional workflow artifact, never converts failure to pass, and has lower precedence than the existing abnormal primary-cause classification; and `TEST-M5-CI-FIRST-FAILURE-LEDGER-001` verifies head-and-tail retention, exact scalar bounds, existing-cap interaction, worker-pool and partition identity, lifecycle fallback, zero reruns, bounded omission, redaction, cause precedence, and fail-closed source rejection.

## Assumptions and constraints

- The required matrix remains exactly Ubuntu, Windows, and macOS on Node.js 24.
- The published package runtime remains Node.js `>=20`.
- Existing candidate-gate OIDC, signature, candidate-tree, Git LFS, and
  single-envelope trust boundaries remain mandatory.
- Local development-loop optimization and general SDD evidence automation are
  downstream changes, not hidden scope in this requirement set.
