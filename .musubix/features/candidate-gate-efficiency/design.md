# Candidate gate efficiency design

## DES-M5-CI-EFFICIENCY-001: Canonical candidate execution plan
Responsibilities: Provide the single versioned source of truth for command ownership, test partitions, worker pools, execution-slot budgets, retry prohibition, and timeout budgets; validate the plan before candidate preconditions or command execution; project its digest into the gate-input fingerprint.
Interfaces: `.musubix/candidate-execution-plan.json`; `CandidateExecutionPlan`, `CandidateCommandPlan`, `CandidatePartitionPlan`, `loadCandidateExecutionPlan()`, `validateCandidateExecutionPlan()`, `candidateExecutionPlanDigest()`, and `candidateExecutionPolicyProjection()` in `packages/analysis/src/candidate-execution-plan.ts`; plan projection in `packages/analysis/src/candidate-gate.ts`; configuration and fingerprint integration in `packages/analysis/src/config.ts` and `packages/analysis/src/gate.ts`; closed command definitions and `testRuntime.inputs` in `.musubix/config.json`; `TEST-M5-CI-RESOURCE-PLAN-001` in `tests/candidate-execution-plan.test.ts`.
Constraints: The plan schema is closed and canonical JSON. It contains exactly the existing seven top-level command names in configured order and no retry field whose value can exceed zero. Each test-owning command declares deterministic include and exclude selectors, ordered partitions, scheduler waves, pool type, `maxWorkers`, per-test fanout, termination allowance, and report merge order. The loader derives each command's authoritative `TEST-*` inventory from its approved selectors and repository source annotations, rejects missing, duplicate-within-command, overlapping-within-command, or unplanned identities, and permits cross-command duplication only when both command ownership sets explicitly name the identity. The maximum simultaneous sum of one logical slot for the runner-launched command root, declared Vitest worker slots, and declared counted nested-process fanout slots is `candidatePlannedExecutionSlots` and cannot exceed 16; repository-local direct executables replace npm/npx wrapper process trees inside the schedulers. `.musubix/config.json` remains the source of truth for closed command invocations and final timeout values. Before those values can change, one `workflow_dispatch` run of `.github/workflows/candidate-calibration.yml` executes the complete planned seven-command shape exactly once without retries in three matrix jobs on Ubuntu, Windows, and macOS from `calibrationSourceCommit`. Calibration uses five step maxima of 1, 2, 28, 1, and 1 minutes inside a 35-minute no-credit job. Its command-plus-formal sum is 1,440,000 milliseconds, its exact outer budget is 1,485,000 milliseconds, and its precondition/post-condition/reserve additions produce a 1,665,000-millisecond gate budget inside the 28-minute step. Calibration continues after a completed nonzero command exit only for diagnostics; accepted calibration requires every region and command to complete successfully, and any nonzero, timed-out, deadline-truncated, runner-lost, report-missing, or acknowledgment-incomplete region invalidates calibration. The three signed no-credit envelopes contain completed pre-signing per-command, per-partition/wave, merge, bounded-termination, precondition, post-condition, persistence, and pre-gate-phase durations; authoritative bootstrap, preparation, signing, and upload durations come from Jobs API step timestamps. `.musubix/candidate-timeout-calibration.json` binds the one run ID, three job IDs and first attempt, API/OIDC/envelope/artifact digests, repository/source/change/generation/matrix context, timeout-excluded plan-shape and gate-input digests, per-job LFS-manifest digests, common logical LFS closure, and maximum completed three-OS duration for each region. `calibrateCandidateTimeouts()` in `packages/analysis/src/candidate-execution-plan.ts` computes `ceil(maximum / 1000) * 1000 * 3 / 2`, subject to the approved candidate caps. The command-shape digest includes command order, executables, argv, selectors, partitions, waves, pools, reports, and launcher/runtime inputs but excludes timeout/cap/calibration values and the calibration file. The timeout-excluded gate-input digest covers schema, repository ID, CHANGE, generation, and the non-timeout config projection, explicitly excludes candidate commit, and preserves all other byte-equivalent inputs; source/final commit identity is verified separately by the direct-parent and limited-tree-diff rule. At the source commit, the calibration manifest input is one canonical absent sentinel; the final commit replaces it with the file digest, and both values are excluded only from the timeout-excluded projection. If any candidate cap cannot retain the exact 3/2 margin, calibration fails and the scheduler or region must be optimized and remeasured. The final candidate is a direct child of the source and may change only the calibration file, config timeout values, and plan timeout/calibration fields; the calibration workflow blob and all other config/input bytes remain identical. The exact accepted values are copied into config and the final plan and equality-checked before execution. For every test-owning command, the loader also rejects a scheduler whose longest sequential wave path plus merge and bounded-termination allowances exceeds its calibrated timeout. Calibration acceptance live-revalidates the source `head_sha`, workflow/event/repository identity, attempt one, three jobs/artifacts, OIDC envelopes, and pass-only non-censored regions. The calibration workflow identity and no-credit envelope status are rejected by candidate checks, release readiness, stability ingestion, and candidate-workflow Runs queries. The `test`, `codegraph-tests`, and `compatibility` command definitions invoke their owning schedulers. `testRuntime.inputs` and the code-owned `testRuntimeProfile` constant contain the same validated list: the plan, calibration-manifest path/sentinel, all three schedulers, the counted launcher, `candidate-execution-plan.ts`, `candidate-stability.ts`, `scripts/verify-lfs-checkout.mjs`, and every existing runtime/coordinator input; a mismatch between those lists fails before fingerprinting. The final plan and calibration digests are computed before the final gate-input fingerprint and are included in the fingerprint, candidate context, runtime dispatch, signed result, and stability evidence.

## DES-M5-CI-EFFICIENCY-002: Counted partition scheduler and aggregate report merger
Responsibilities: Execute the `test`, `codegraph-tests`, and `compatibility` command-owned corpora through deterministic bounded partitions while retaining exactly one top-level invocation per closed command and one fresh aggregate report per command.
Interfaces: `scripts/run-candidate-tests.mjs`; refactored `scripts/run-codegraph-tests.mjs`; `scripts/run-compatibility-tests.mjs`; `scripts/test-runtime/counted-launcher.mjs`; `CandidateSlotLease`, `CandidateSlotObservation`, `acquireCandidateSlots()`, and `releaseCandidateSlots()` in `packages/analysis/src/candidate-execution-plan.ts`; `CandidatePartitionDispatch`, `CandidatePartitionAcknowledgment`, `CandidatePartitionAcknowledgmentManifest`, and composite acknowledgment validation in `packages/analysis/src/test-runtime.ts`; partition metadata support in `scripts/test-runtime/coordinator-reporter.mjs`; aggregate Vitest report parsing and merging in `packages/analysis/src/adapters.ts`; command execution and independent manifest validation in `packages/analysis/src/gate.ts`; `TEST-M5-CI-RESOURCE-PLAN-001` in `tests/candidate-execution-plan.test.ts`.
Constraints: Each top-level command process remains the process observed by the existing test-runtime request, dispatch, result, and reporter bindings. The validated dispatch creates a nonce-bound slot ledger under the private matrix run root. A logical command root owns one slot; the scheduler and counted launchers acquire an entire request atomically by attempting numbered lease directories in global ascending order and releasing every provisional lease if the full request cannot be acquired. They append nonce-, PID-, partition-, count-, and monotonic-time-bound observations and release only their own leases after close or bounded process-tree termination. The gate-side coordinator rejects malformed, foreign, over-capacity, leaked, or missing observations, calculates the observed maximum from the ledger, and binds that maximum and the ledger digest into the independently derived top-level acknowledgment and result. No launcher can wait past its partition deadline, and no stale lease is reused; runner cleanup removes leases only after the bound process tree is confirmed terminated. The scheduler starts only plan-declared child groups and never retries a failed group. High-memory LFS files, nested worker-pool files, and real-concurrency files run in single-partition isolation with plan-declared worker and fanout bounds; regular files use the remaining bounded worker slots. Child groups use repository-local Vitest, canonical file paths or file URLs as required, explicit report paths under the matrix run root, and no shell. Each child reporter writes a partition acknowledgment containing its plan and wave ordinals, dispatch digest, execution binding, observed Vitest argv, selected-file and worker-packet inventory, native-report path and digest, observed slot maximum, process status, exit code or signal, and first lifecycle failure. The scheduler writes only a sorted manifest of acknowledgment paths and digests; after the command exits, the gate-side coordinator independently loads every partition acknowledgment, re-validates its binding and inventories against the plan and dispatch, rejects missing or duplicate files/workers across partitions, and then derives the one existing top-level acknowledgment consumed by `test-runtime.ts`. A missing or invalid partition acknowledgment fails that named partition instead of collapsing to an unbound command acknowledgment error. The report merger consumes only the independently accepted manifest, rejects duplicate or missing command-owned test IDs, sorts by plan ordinal and UTF-8 test ID, preserves native failed assertions, and emits one adapter-compatible report plus one command exit. Existing Code Graph operation reports stay isolated per authoritative test and keep their approved counters and maxima. The static source rule rejects direct process creation inside authoritative test files unless it is the counted launcher implementation. Candidate-reachable product-code launches use `packages/analysis/src/process.ts` with an injected slot provider when the dispatch nonce is present; a Code Graph impact inventory rejects another reachable launch path, while non-candidate product execution remains unchanged. Synchronous Git fixture operations migrate to counted helper functions rather than receiving an exemption. Each scheduler also preserves targeted Red/Green invocation by accepting the existing `--test-id`, `--report`, adapter report, and configured `tddArgs` forms; targeted mode executes exactly one selected identity through the same counted launcher, emits one fresh report, and never enters or receives matrix stability credit.

ADRs: ADR-0044
Depends-On: DES-M5-CI-EFFICIENCY-001 DES-M5-CI-004 DES-M5-015

## DES-M5-CI-EFFICIENCY-003: Portable fixture and runtime canonicalization boundary
Responsibilities: Centralize platform-aware temporary roots, canonical filesystem paths, Node.js module URLs, executable/argv normalization, and logical Git LFS observations used by candidate tests and runtime bindings.
Interfaces: `tests/fixtures/portable-paths.ts`; counted process helpers in `tests/fixtures/counted-process.ts`; path and invocation normalization in `packages/analysis/src/process.ts`; canonical recovery-root validation in `packages/analysis/src/generation10-recovery.ts`; runtime executable, argv, selected-file, dispatch, acknowledgment, and result normalization in `packages/analysis/src/test-runtime.ts`; LFS logical content checks in `packages/analysis/src/tdd-source-lfs.ts`, `packages/analysis/src/tdd-source-storage.ts`, and `tests/git-lfs-distribution.test.ts`; affected worker and concurrency fixtures in `tests/test-runtime-worker.test.ts`, `tests/concurrency-runner-clock.test.ts`, `tests/change-lease.test.ts`, `tests/workspace-batch-checkpoint.test.ts`, and `tests/candidate-integration-orchestration.test.ts`; `TEST-M5-CI-PORTABLE-EXECUTION-001` in `tests/candidate-portable-execution.test.ts`.
Constraints: Temporary paths derive from an injected authorized root or `node:os.tmpdir()` and are created before `mkdtemp`; no test constructs `/tmp`, `\tmp`, or a synthetic platform root directly. Module subprocess arguments use `pathToFileURL()` and consumers use `fileURLToPath()` before filesystem access. Windows drive and UNC roots are accepted only by Windows-mode canonicalization, POSIX roots only by POSIX-mode canonicalization, and mixed separators, traversal, device paths, alternate data streams, and case-ambiguous substitutions are rejected. Runtime binding hashes use one platform-tagged canonical path projection on producer and validator. Concurrency tests retain their deterministic operation/state assertions and move hosted-runner elapsed observations to informational diagnostics. Git LFS verification retains the exact three 100 MB boundaries, pointer grammar, cache integrity, logical SHA-256, and source-mode obligations while avoiding worktree-byte or executable-bit assumptions unsupported by the active platform.

ADRs: ADR-0044

## DES-M5-CI-EFFICIENCY-004: Job-relative deadline and signed timing projection
Responsibilities: Replace the superseded candidate timeout contract with one job-start-relative deadline, bounded precondition/gate/postcondition regions, and signed pre-signing timing metadata while guaranteeing a failure envelope can be uploaded before the 20-minute artifact deadline.
Interfaces: timeout projection in `.musubix/config.json`; five bounded pre-terminal steps and `actions: read` permission in `.github/workflows/candidate-gate.yml`; `.github/actions/prepare-candidate/action.yml`; `scripts/verify-lfs-checkout.mjs`; `CandidateLfsClosureManifest`, `verifyCandidateLfsClosureManifest()`, and cheap worktree closure probes in `packages/analysis/src/candidate-gate-runner.ts`; `resolveCurrentJobTiming()` in `.github/scripts/resolve-candidate-job-timing.mjs`; `candidateGateOuterTimeoutMs()`, deadline validation, `CandidateGateRunnerResult` timing fields, and injected clocks in `packages/analysis/src/candidate-gate-runner.ts`; workflow-protected dependency-free failure synthesis and OIDC signing embedded in `.github/workflows/candidate-gate.yml`; workflow start propagation in `.github/scripts/run-candidate-gate-wrapper.mjs`; result parsing in `packages/analysis/src/candidate-gate.ts`; `TEST-M5-CI-EFFICIENT-ORCHESTRATION-TIMEOUT-001` in `tests/candidate-gate-efficient-timeout.test.ts`.
Constraints: The workflow grants only `contents: read`, `actions: read`, and `id-token: write`; `actions: read` exists solely for current-run job timing and stability projections. Candidate mode has exactly five timeout-bearing top-level steps with maxima of 60,000, 120,000, 840,000, 60,000, and 60,000 milliseconds; calibration mode uses 60,000, 120,000, 1,680,000, 60,000, and 60,000 milliseconds inside its separate no-credit workflow. The 60,000-millisecond inline Node/Git bootstrap, whose source is embedded in the workflow because repository files do not yet exist, checks Git LFS, sets `core.autocrlf=false` before worktree materialization, initializes `origin` with the canonical HTTPS repository URL, performs a full-history fetch of only the immutable candidate with a process-local non-persisted authorization header, removes that header, runs `git lfs install --local`, fetches the complete LFS object closure without materializing it, and checks out pointer content with skip-smudge scoped only to that checkout child. The 120,000-millisecond local preparation action resolves authoritative job timing first, configures Node 24, verifies and materializes the exact LFS closure from already-fetched local objects, restores or installs lockfile-bound dependencies, and builds the runner. `scripts/verify-lfs-checkout.mjs` accepts the preparation action's absolute deadline, replaces its independent fixed timers with remaining-time-aware operations, reuses one pre-hydration `rev-list --objects --missing=error` result while preserving the per-commit `read-tree`/`check-attr` oversize check, and emits a canonical manifest under `RUNNER_TEMP`. The manifest binds a fresh dispatch nonce, GitHub run ID and attempt, API job-timing projection digest, repository identity, candidate commit, object set, pointer set, logical digests, source modes, and script/config digests. Its digest is captured before the gate, included in the runner input, signed result, six-envelope stability binding, and calibration envelope. Generation 50's Windows observations provide only a feasibility baseline: pre-check/config/checkout with LFS download took 36 seconds, setup/LFS/npm/build took 123 seconds, and the full pre-gate path took 159 seconds. Calibration acceptance uses the Jobs API step timestamps, not in-step clocks, and candidate dispatch is blocked until bootstrap observes at most 40,000 milliseconds, preparation at most 80,000 milliseconds, and their 3/2 margins fit the fixed step bounds. The runner precondition independently validates the manifest schema, digest, nonce, run/job/context binding, and current pointer/object availability instead of rescanning full history; the post-condition validates the same immutable manifest plus unchanged Git tree/status and current pointer/object availability. Their calibrated durations must retain the required 3/2 margin within 60,000 milliseconds, eliminating the former three full-history scans. Candidate mode uses the 840,000-millisecond gate and at-most-660,000-millisecond outer budget; calibration mode uses the separately validated 1,665,000-millisecond gate budget and 1,485,000-millisecond outer budget inside its 1,680,000-millisecond step. `candidateGateOuterTimeoutMs()` receives an explicit closed mode and cannot apply one mode's bounds to the other. Candidate mode's job-start-relative deadline preserves the 20-minute artifact bound; calibration mode preserves the final 120,000 milliseconds of the 35-minute job for signing/upload/terminal enforcement. The separate 60,000-millisecond signing step executes under `if: always()` and contains only workflow-embedded dependency-free code: it synthesizes workflow-stage failures when needed, validates any runner result and LFS-manifest digest, requires candidate config to equal the workflow-embedded OIDC audience constant when config exists, and signs the failing or passing result. Candidate code and worktree files never supply the signing implementation or fallback audience. The fifth step is `actions/upload-artifact@v4` under `if: always()` with a 60,000-millisecond timeout. The preparation action records the API job start, run attempt, response time, and projection digest and rejects excessive clock skew. The signed envelope contains mode, run ID, run attempt, plan, calibration, and LFS-manifest digests when available, API timing projection, runner-observed pre-signing completion timestamp, and nonnegative pre-signing elapsed milliseconds; missing candidate bindings fail and no-credit calibration bindings can never receive candidate stability credit.

## DES-M5-CI-EFFICIENCY-005: GitHub first-attempt stability verifier
Responsibilities: Query GitHub Actions run, attempt, job, and artifact metadata; bind it to OIDC-signed envelopes; persist two-run stability evidence; expose release-readiness diagnostics without replacing the later run's authoritative gate set.
Interfaces: `GitHubCandidateRun`, `CandidateRunTiming`, `CandidateStabilityEvidence`, `fetchCandidateRun()`, `fetchCandidateRunAttempt()`, `fetchCandidateJobs()`, `fetchCandidateArtifacts()`, `verifyCandidateRunTiming()`, `verifyCandidateStabilityPair()`, `recordCandidateStability()` and `loadCandidateStability()` in `packages/analysis/src/candidate-stability.ts`; `candidate-gate stability <first-run-id> <second-run-id> --repository <owner/repo>` in `packages/cli/src/main.ts`; release/gate integration in `packages/analysis/src/candidate-gate.ts`, `packages/analysis/src/gate.ts`, and `packages/analysis/src/release-manifest.ts`; journal kind `candidate-gate-stability`; `TEST-M5-CI-STABILITY-PROOF-001` in `tests/candidate-stability.test.ts`.
Constraints: The client uses the GitHub REST API with a caller-supplied token and never persists that token. It resolves the current workflow identity only from repository identity plus `.github/workflows/candidate-gate.yml`, then fetches all workflow-dispatch runs for that workflow and candidate `head_sha` without filtering by run attempt; no numeric workflow ID is committed or accepted as an alternate identity. Accepted runs have current `run_attempt: 1`, first-attempt endpoint conclusion `success`, exactly three successful expected jobs, and exactly three expected artifacts. Job `started_at` and matching artifact `created_at` produce each platform's end-to-end duration and must be at most 1,200,000 ms. The two accepted runs are adjacent in the filtered creation-order list; any intervening run, rerun, unavailable first attempt, non-success conclusion, missing platform, missing artifact, context mismatch, plan mismatch, or OIDC/envelope failure blocks credit. The persisted evidence hashes the exact API projections and six envelopes and records both run IDs, attempt-one conclusions, job/artifact identities and timestamps, adjacency cursor, workflow path/resolved identity, and verification time. Every release-readiness and candidate-gate status evaluation re-fetches both candidate runs, both first-attempt endpoints, the complete matching candidate-run sequence, six jobs, six artifacts, and the approved calibration run's first-attempt endpoint, three jobs, three artifacts, Jobs API timing projection, and three OIDC envelopes; it rejects changed attempts, conclusions, adjacency, identities, timestamps, source/final relation, calibration digest, or envelopes. Evidence is also stale when the candidate commit, generation, repository identity, plan digest, calibration digest, source/final relation, gate-input fingerprint, workflow identity, or later authoritative gate set changes.

## DES-M5-CI-EFFICIENCY-006: First-attempt diagnostic ledger projection
Responsibilities: Extend existing candidate failed-test diagnostics with partition, worker-pool, lifecycle-stage, and bounded head-and-tail native failure context without adding a field, artifact, trust source, retry, or pass input.
Interfaces: transient failed-test carrier in `packages/analysis/src/test-runtime.ts`; structured failed-test projection in `packages/analysis/src/gate.ts`; redaction, scalar bounding, omission accounting, and check sanitization in `packages/analysis/src/candidate-gate-runner.ts`; partition metadata from the scheduler and coordinator reporter; `TEST-M5-CI-FIRST-FAILURE-LEDGER-001` in `tests/candidate-first-failure-ledger.test.ts`.
Constraints: Enrichment consumes only current-run, digest-bound, regular non-symbolic structured reports already authorized by REQ-M5-CI-008 and reuses `checks[].diagnostics`. Per-command 100-entry and envelope 200,000-scalar limits remain authoritative. Native messages of at most 1,000 scalars are retained whole; longer messages retain the first 400 scalars, the exact omitted-count marker, and the maximum fitting tail within 1,000 scalars. Existing 500-scalar title and 1,800-scalar composed-message limits remain unchanged. Partition and worker-pool identifiers come only from the validated plan/dispatch, lifecycle stages come only from runner observations, path categories are emitted instead of private absolute paths, and all text passes the existing carry-safe redactor before truncation. Invalid enrichment is dropped as a unit, existing abnormal primary-cause precedence remains unchanged, and no diagnostic participates in pass computation.
Requirements: REQ-M5-CI-EFFICIENCY-004
ADRs: ADR-0044
Depends-On: DES-M5-CI-EFFICIENCY-001 DES-M5-CI-EFFICIENCY-002 DES-M5-CI-008
