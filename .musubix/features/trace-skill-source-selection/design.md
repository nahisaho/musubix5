# Trace Skill source selection design

## DES-M5-TRACE-SKILL-001: Repository Skill trace selector
Responsibilities: Recognize the current and pinned legacy musubix source repositories, select repository-owned Skill Markdown files only for those identities, and remove Markdown code-example regions from annotation discovery without changing line locations.
Interfaces: `traceInputs(root)`, `buildTrace(root, persist)`, code node `CODE-M5-TRACE-SKILL-001` in `packages/analysis/src/trace.ts`, test node `TEST-M5-EVIDENCE-SKILL-INPUT-001`, the shared exported `isRecognizedMusubixSource(manifest)` predicate in `packages/analysis/src/files.ts`, and an internal line-preserving Markdown code mask that substitutes for `maskGenericStrings` when `genericCommentBlocks` constructs and parses its searchable annotation text for `isSkillSource(path)` while line numbers continue to come from the original text.
Constraints: Current identity is the exact pair `package.json.name === "musubix5"` and object-form `package.json.repository.url === "https://github.com/nahisaho/musubix5.git"`; pinned legacy identity is the exact pair `musubix3` and `https://github.com/nahisaho/musubix3.git`. Missing, unreadable, malformed, shorthand, non-object, non-string, or non-exact manifest fields fail closed as non-matches without throwing. Normative artifacts and supported-language source selection are independent of repository identity. Markdown masking applies only to Skill Markdown and replaces the generic quote/string mask for those files; apostrophes and quotation marks in prose therefore cannot suppress a later declaration. Every non-Markdown source retains the current string/comment masking path, including indented Python and YAML annotations. The scanner classifies line structure from the original text, first masks fenced blocks, then top-level indented blocks, then inline spans only in unmasked text. A leading BOM remains in the output but is ignored when recognizing first-line structure. A fence opener has zero to three leading spaces and a run of at least three backticks or tildes; its closer has zero to three leading spaces, the same character, and a run at least as long. The masked region includes both delimiter lines, and an unterminated fence masks through EOF. An indented block starts only at document start or after an originally blank line with at least four spaces or one tab; when a preceding nonblank line exists it must begin at column zero and must not be a list marker matching `[-+*]` or `\d+[.)]` followed by whitespace. It masks consecutive indented lines and internal originally blank lines, terminates before the first originally nonblank line lacking the required indentation, excludes trailing blank lines from the block, and does not start immediately after a nonblank fence closer, interrupt a paragraph, or consume a list continuation. An inline span uses matching equal-length backtick runs, closes at the first matching run before the next originally blank line, and an opener without such a closer masks nothing. Masking replaces every non-CR/non-LF character in code examples with a space while preserving total UTF-16 string length, `\r`, `\n`, a leading BOM, and reported line locations. Candidate comment ranges are discovered from searchable masked text, and Skill node IDs plus `@implements`, `@verifies`, and `@design` targets are parsed only from that masked slice; original text is used only to calculate the preserved line location. Thus an opener or real annotation outside a code example cannot import a masked closer, ID, or target from inside the example. Outside masked regions, existing annotation syntax, duplicate detection, diagnostics, persistence, and strict-check rules are unchanged. Tests cover prose with unmatched apostrophes and quotes before a real declaration; a stray prose `/*` before a fenced annotation example; a mixed comment containing one real annotation and a fenced example that must emit only the real node and targets; three-space-indented fences; masked delimiter lines; longer closing fences; unterminated fences; original-text blank-line classification; top-level indented blocks and termination; list continuations; single- and double-backtick spans; unmatched and cross-blank-line backticks; first-line BOM recognition; non-Markdown indented annotations; stable line locations; and absence of the example nodes `CODE-FEATURE-001` and `TEST-FEATURE-001` from the real repository graph. The parser does not attempt full CommonMark rendering and adds no runtime dependency.
Requirements: REQ-M5-EVIDENCE-008
ADRs: ADR-0018

## DES-SESSION-SCOPED-DEVELOPMENT-001: Integrated change workflow contract
Responsibilities: Define the repository-owned integrated change Skill as the mandatory entrypoint for a fresh development request and enforce validated, explicitly approved requirements and design before implementation.
Interfaces: `.github/skills/sdd-change/SKILL.md`; trace node `CODE-SESSION-SCOPED-DEVELOPMENT-001`; contract test node `TEST-SESSION-SCOPED-DEVELOPMENT-001`.
Constraints: An unnamed natural-language development request creates a fresh CHANGE and feature scope; only an explicitly named existing CHANGE may continue prior work. Prior-session artifacts are historical context, validation is not approval, approval is never inferred, and absent, stale, invalid, or edited requirements or design return control to the corresponding specification phase before implementation.
Requirements: REQ-SESSION-SCOPED-DEVELOPMENT-001 REQ-SESSION-SCOPED-DEVELOPMENT-002
ADRs: ADR-0019

## DES-SESSION-SCOPED-DEVELOPMENT-002: Requirements workflow contract
Responsibilities: Define the repository-owned requirements Skill's fresh feature scope, explicit requirements-approval boundary, and handoff to design.
Interfaces: `.github/skills/sdd-requirements/SKILL.md`; trace node `CODE-SESSION-SCOPED-DEVELOPMENT-002`; contract test node `TEST-SESSION-SCOPED-DEVELOPMENT-001`.
Constraints: Each unnamed development request uses a fresh feature requirements artifact. Prior-session artifacts do not authorize reuse, requirements validation is not human approval, design begins only after explicit current requirements approval, and rejection or an intervening requirements edit requires renewed review and approval.
Requirements: REQ-SESSION-SCOPED-DEVELOPMENT-001 REQ-SESSION-SCOPED-DEVELOPMENT-002
ADRs: ADR-0019
