# Wave 0 release operations requirements

## REQ-M5-WAVE0-COMPLETION-001: Preserve completed CHANGE validation context
Priority: must
Type: functional
Pattern: event-driven
Statement: When an active CHANGE generation is completed, the system shall preserve that generation as the deterministic validation context for the completed CHANGE without selecting unrelated historical workflow declarations.
Acceptance: A fixture containing a release-ready active CHANGE, artifact-bound requirements/design/release approvals, candidate snapshot and gate evidence, unrelated historical workflow declarations, and only inert stale workflow waivers can record its terminal `sdd-change complete` declaration and then transition its CHANGE document to `status: completed`; subsequent `gate`, `status`, repository-wide and domain-scoped approval validation, workflow validation, candidate snapshot projection, and candidate-gate validation select the completed CHANGE's final generation, do not validate unrelated historical declarations, keep the existing approvals and candidate evidence current, expose no active workflow waiver, and retain `gate.ready: true`. For schema-version-1 chronology, a completed generation is defined by a `status: completed` CHANGE document whose current `activeGeneration` is a positive integer and whose current generation has a quality checkpoint; no new chronology field or migration is required. When no CHANGE document is active, read-only validation first selects the completed document with the highest numeric CHANGE identifier, then validates its chronology eligibility; if that newest completed document has `activeGeneration: null`, missing chronology, or no current quality checkpoint, validation fails closed with repair guidance and never falls back to an older eligible CHANGE. Equal numeric identifiers or malformed identifiers fail closed rather than using timestamps. If the terminal declaration was not recorded before the document became completed, validation remains scoped to that CHANGE and reports non-waivable `CHANGE_COMPLETION_DECLARATION_MISSING` with recovery guidance to restore `status: active`, record the declaration, and complete the document again. If a different CHANGE document is active, implicit operations select only that active CHANGE while explicit maintenance validation can still resolve an identified completed CHANGE and its final generation. Read-only `gate`, `status`, `approval validate`, workflow verification, candidate snapshot projection, and candidate-gate validation opt in to the completed context explicitly; default `resolveChangeContext()` and `activeChangeContext()` behavior remains active-only. `workflow-record`, `change-record`, `tdd red|green|refactor|repair|migrate|void`, `candidate-snapshot create|delete`, candidate workspace registration, candidate-gate ingestion, approval recording, and parallel lifecycle transitions remain fail-closed for a completed CHANGE with their existing lifecycle diagnostics. If the repository contains no CHANGE documents, read-only workflow validation retains its existing chronology-based selection and falls back to all workflow history only when no chronology entry has an active generation. The completion context does not reactivate an abandoned generation, fabricate missing chronology, permit new mutable evidence, or broaden workflow waiver scope.
Formal: {"kind":"transition","from":"active-generation","event":"complete-change","to":"completed-generation-context"}

## REQ-M5-WAVE0-HANDOFF-001: Preserve NUL-delimited Git porcelain records
Priority: must
Type: functional
Pattern: event-driven
Statement: When parallel handoff checks candidate worktree cleanliness, the system shall parse NUL-delimited Git porcelain records without trimming status bytes or path characters.
Acceptance: A candidate at the exact plan base with a first porcelain record equal to an unstaged modification under `integratorOwnedPaths` passes the dirty-at-base check; equivalent staged and untracked owned paths also pass; a path outside the declared ownership still fails with `PARALLEL_CANDIDATE_DIVERGED` and reason `dirty-at-base`; rename and copy records preserve and validate both source and destination paths; leading spaces, leading dots, non-ASCII path text, and the optional final NUL are handled byte-for-byte; and every existing caller of the trimmed Git helper, including the non-`-z` porcelain cleanliness check, retains its current textual-output behavior.

## REQ-M5-WAVE0-CANDIDATE-REF-001: Emit an immutable candidate dispatch ref
Priority: must
Type: functional
Pattern: event-driven
Statement: When candidate-gate context is requested for a release candidate, the system shall emit deterministic immutable-ref guidance that binds workflow dispatch to the exact candidate commit.
Acceptance: `candidate-gate context --json` returns the candidate commit, a deterministic branch name `candidate/<lowercase-change-id>-g<generation>-<first-12-candidate-commit-hex>`, and non-interactive command descriptors containing an executable plus an argument array for verifying or creating the ref at exactly the candidate commit, pushing it without overwriting a remote ref that points elsewhere, dispatching `.github/workflows/candidate-gate.yml` with `--ref <candidate-ref>` and every required workflow input, and deleting the local and remote ref only after envelope ingestion. If the local or remote ref already resolves to the same commit, the guidance is idempotent; if either resolves to a different commit, it reports a collision and does not recommend force-moving the ref. Human-readable output and `README.md`/`README-ja.md` explain that raw commit SHAs are not accepted as `workflow_dispatch` refs, that `.github/workflows/candidate-gate.yml` must exist on both the repository default branch and the candidate commit, that the ref must not advance until every dispatched envelope is ingested, and that an advanced branch tip produces an OIDC `job_workflow_sha` mismatch. The existing strict attestation invariant requiring `job_workflow_sha` to equal the candidate commit remains unchanged; explicit candidate context remains fingerprint-bound; and no command automatically pushes, dispatches, or deletes a Git ref.
