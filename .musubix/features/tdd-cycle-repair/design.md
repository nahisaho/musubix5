# Scoped TDD cycle repair design

## Architecture constraints

- Repair is a maintenance operation over existing TDD evidence. It never records
  Red, Green, Refactor, migration, or void evidence and never edits or removes an
  existing cycle, phase, chain record, order record, or repair record.
- The stable public selector is the tuple `(testId, cycleId)`. Array position,
  latest-by-file-order, test ID alone, and mutable diagnostic text are not
  selectors.
- A repair record is authoritative only when its payload, unique TDD chain
  record, predecessor digest, and monotonic order record all verify. Malformed
  repair data grants no suppression, replacement, retirement, coverage, or
  source-currency effect.
- A target may receive exactly one valid repair. Replacement and retirement are
  mutually exclusive terminal dispositions of that target. Replays of the same
  derived operation identity return the persisted result; a later request
  cannot append a second disposition.
- Replacement does not copy or mutate phase evidence. It links the stale target
  to a separately recorded, current, authoritative Red/Green cycle. Retirement
  is explicitly non-credit and cannot itself satisfy requirement coverage or
  source currency.
- `tdd void` remains limited to a dangling cycle with an eligible fallback, and
  `tdd migrate` remains limited to a current fingerprint change on a verified
  Green terminal. Neither command repairs stale parallel provenance.
- Every rejected repair performs zero writes to `.musubix/evidence/tdd.json`,
  `.musubix/evidence/order.json`, and the normal journal. A previously journaled
  operation may be completed by explicit `--resume` or, only for eligible
  `journal-invalid` / `identity-mismatch` / `partial-projection-mismatch` state, closed by explicit
  audited `--abandon-pending`; normal repair requests never perform recovery.
  A new request or existing TDD writer encountering a pending repair fails
  closed without recovering it. Validation and idempotency lookup complete
  before the first append for every new request.
- The additive command, JSON fields, help text, diagnostics, and exit mappings
  are compatibility extensions governed by REQ-M5-COMPAT-013.

## Repair state and precedence

For a target cycle, the effective disposition is:

1. no valid repair: evaluate the cycle under the existing TDD rules;
2. valid replacement: suppress the target from coverage, currency, work-event,
   supersession, and missing-phase selection, then evaluate the linked
   replacement cycle exactly once under the existing rules;
3. valid retirement: suppress the target from coverage, currency, work-event,
   supersession, and missing-phase selection, contribute no repair credit, and
   expose only the recorded `fallbackCycleId` as the repair's fallback. Its
   eligibility at admission is fixed in the repair record; its later ordinary
   eligibility may change without invalidating or retargeting that repair.

Invalid or duplicate repair records do not participate in this precedence and
produce chain/repair diagnostics. A replacement cycle remains an ordinary cycle
and is never cloned into the target. A replacement target cannot be itself,
cannot form a repair cycle, and cannot already have a valid replacement or
retirement. These rules guarantee at most one effective current cycle for the
repaired requirement batch without hiding diagnostics from unrelated cycles.

## DES-M5-TDD-REPAIR-001: Append-only repair record store
Responsibilities: Extend schema-v1 TDD evidence with append-only repair and non-credit abandonment records, bind each record to one target cycle and one deterministic operation identity, recover valid journaled operations across every crash boundary, close only specifically unrecoverable pending operations through audited abandonment, append corresponding monotonic-order and repair hash-chain entries where applicable, and preserve every pre-existing cycle and hash byte-for-byte.
Interfaces: `TddRepairRecord`, `TddRepairDisposition`, `TddRepairJournalRecord`, `TddRepairPartialFragment { kind: "order" | "repair-projection" | "repair-chain", index, sha256 }`, `TddRepairAbandonmentRecord { operationId, testId, targetCycleId, failureCause, pendingJournalSha256, partialFragments: TddRepairPartialFragment[], approver, reason, order, recordedAt }`, `TddRepairResult`, `TddRepairAbandonmentResult`, `appendTddRepair(root, request)`, `resumeTddRepair(root, operationId)`, `abandonPendingTddRepair(root, operationId, approver, reason)`, `.musubix/evidence/tdd.json.repairs[]`, `.musubix/evidence/tdd.json.repairAbandonments[]`, journal schemas `tdd-repair-v1` and `tdd-repair-abandonment-v1`, TDD chain phase `repair`, evidence-order phases `repair:<operationId>` and `repair-abandonment:<operationId>`.
Constraints: `TddRepairRecord` contains `operationId`, `requestSha256`, `targetCycleId`, `testId`, `requirementId`, effective `changeId` and `generation`, the target's exact persisted `binding` and `parallel` identities, exactly one of `replacementCycleId` or `retired: true` plus `fallbackCycleId`, trimmed `approver`, trimmed `reason`, `order`, and `recordedAt`; canonical request JSON has keys in the fixed order `schemaVersion`, `testId`, `targetCycleId`, `disposition`, `replacementCycleId`, `approver`, `reason`, uses `replacementCycleId: null` for retirement, trims `approver` and `reason`, and excludes `root`, `json`, `confirm`, timestamps, order, and derived bindings; `requestSha256` is the lowercase SHA-256 of those bytes and `operationId` is exactly `tdd-repair:<requestSha256>`; the journal idempotency key is exactly the operation ID and persists the request digest, normalized request, validated target/replacement or retirement-fallback snapshots, and one derived `recordedAt`; normal repair and existing TDD writer paths inspect pending `tdd-repair-v1` records read-only and return `TDD_REPAIR_PENDING` with operation/target detail without writing; `resumeTddRepair` may recover the exactly named structurally valid pending operation; `abandonPendingTddRepair` may act only when a valid envelope fixes `operationId`, `testId`, and `targetCycleId` and resume classifies the entry as `journal-invalid`, `identity-mismatch`, or `partial-projection-mismatch`, which is also the closed `failureCause` enum; `pendingJournalSha256` hashes canonical JSON bytes of the entire observed pending journal object; fragment kind maps exactly to `order`=`.musubix/evidence/order.json.records[index]`, `repair-projection`=`.musubix/evidence/tdd.json.repairs[index]`, and `repair-chain`=`.musubix/evidence/tdd.json.chain[index]`; each fragment `sha256` hashes canonical JSON bytes of that observed JSON value; `partialFragments[]` is unique and sorted by kind precedence `order`, `repair-projection`, `repair-chain`, then index; quarantined journal/order/projection/chain fragments remain physically present and byte-identical in their original arrays, and order-log/TDD-chain `sequence`, `previousSha256`, and `recordSha256` continuity continues through them; exact locator/digest matches are excluded only from effective repair projection, coverage credit, source-currency credit, and future cycle selection, while duplicates, changed values, or unlisted operation fragments keep the ledger blocked; before its first append each recovery path validates its prospective complete ledger in memory and after that point performs only deterministic appends; abandonment appends schema `tdd-repair-abandonment-v1` to the normal journal, one monotonic order record, and `repairAbandonments[]`, but no new repair chain entry and no new `repairs[]` disposition; an interrupted abandonment is itself pending and exact command replay appends only its missing prevalidated suffix; it unblocks writers only after all abandonment suffixes exist and validate; abandonment canonical identity is operation ID plus normalized approver/reason, exact replay returns persisted values with `replayed: true`, and divergent reuse fails; every resume derives order, timestamp, hashes, and output from the journaled operation and never appends duplicates; the repair chain payload snapshots the same target identity including candidate binding and hashes the complete repair record; persistence failure cannot expose a success result; repair and abandonment never write into `cycles[]`; the canonical JSON and SHA-256 of every non-target and target cycle remain unchanged; an exact completed normal request derives the same `operationId`, returns the persisted record with `replayed: true`, and appends nothing; any later distinct request for the target returns `TDD_REPAIR_ALREADY_RECORDED`.

## DES-M5-TDD-REPAIR-002: Stable target and replacement validator
Responsibilities: Resolve the exact target from `(testId, cycleId)`, prove that it is the intended stale parallel-bound cycle, validate its immutable identity against phase and chain evidence, and validate a replacement cycle without granting credit or writing state.
Interfaces: `resolveTddRepairTarget(evidence, testId, cycleId)`, `validateTddRepairBinding(target, order, chainIndex, parallelEvidence)`, `resolveTddRepairReplacement(evidence, replacementCycleId, target, context)`, `TddRepairValidation`.
Constraints: normal repair begins with CLI validation, read-only pending detection, complete projected repair-ledger validation, and completed replay lookup in that order; pending detection returns `TDD_REPAIR_PENDING` and never auto-recovers; `--resume` performs named pending lookup, journal identity/schema validation, partial-projection validation, and prospective-ledger validation; `--abandon-pending` performs named pending lookup, valid-envelope validation, resume-failure classification, abandonment replay/conflict validation, and prospective abandonment-ledger validation; when no pending operation or replay exists, selector lookup scans all cycles and requires exactly one global `cycleId` match; a missing or duplicate cycle ID returns `TDD_REPAIR_TARGET_INVALID` with cause `cycle-not-found` or `cycle-id-ambiguous`, while a unique cycle whose test ID differs from the positional test ID returns `TDD_REPAIR_BINDING_MISMATCH`; after stable selection the validator checks prior disposition before resolving authorization: when `approval.domains` is empty it requires current undomained design approval and reports `domain: null`, otherwise it uses the configured domain owning the target requirement and reports that owner name; missing, stale, or wrong-domain approval returns `TDD_REPAIR_AUTHORIZATION_INVALID`; completed replay, resume, and abandonment do not re-evaluate approval; operation scope, immutable binding/source integrity, stale-parallel eligibility, and disposition outcome follow authorization; foreign scope returns target-invalid cause `foreign-operation-scope`, no parallel identity returns `target-not-parallel-bound`, and currently creditable parallel provenance returns `target-parallel-binding-not-stale`; target phase and chain snapshots must agree on test ID, requirement ID, effective CHANGE ID/generation, candidate binding, command, test path, exact parallel tuple `(planId, assignmentId, attempt, worktree, startCommit)`, and the uniquely resolved current trace test node; the trace node path must equal `testPath`, and its current canonical fingerprint must equal both recorded Red and Green test fingerprints, otherwise return `TDD_REPAIR_BINDING_MISMATCH`; the current active or selected maintenance context must equal the target's effective CHANGE ID/generation; replacement candidate binding is canonical-JSON byte equality with the target binding, including both absent as equal; a replacement must be a distinct unrepaired cycle with the same test ID, requirement ID, effective CHANGE ID/generation, exact candidate binding, current authoritative test path/fingerprint, valid linked Red and passing Green, verified order `red < green`, and intact chain; a parallel replacement is classified with `purpose: "tdd-repair"` and must return `pass`; replacement mode requires the named replacement to be the exactly one current eligible cycle; retirement requires exactly one independently eligible fallback and persists its fixed append-time identity; an invalid complete order log invalidates every repair, while an invalid repair payload or linkage returns `TDD_REPAIR_CHAIN_INVALID` except while a valid-envelope pending operation remains eligible for resume/abandon classification; validation never rewrites parallel evidence.

## DES-M5-TDD-REPAIR-003: Repair-aware effective-cycle resolver
Responsibilities: Build one verified repair index, apply replacement/retirement precedence before existing coverage and source-currency selection, and retain diagnostics for every unrelated invalid cycle.
Interfaces: `buildTddRepairIndex(evidence, order, chainIndex)`, `effectiveRepairDisposition(cycleId)`, `repairAwareCycles(cycles, repairIndex)`, existing `effectiveLatestCycle`, `greatestVerifiedEvent`, and requirement-coverage evaluation.
Constraints: index keys are target cycle ID and operation ID, not array position; only a uniquely linked valid repair record participates; `repairAbandonments[]` is validated for audit and pending-state closure but contributes no disposition, repair credit, coverage, source currency, or selected cycle; quarantined fragments remain physically present in the journal, order log, `tdd.json.repairs[]`, and `tdd.json.chain[]`, remain part of monotonic/hash predecessor continuity, and are excluded only from effective repair projection, coverage, source-currency credit, and future cycle selection; replacement suppresses only its target and leaves the linked replacement as one ordinary candidate; retirement suppresses only its target and exposes only the persisted `fallbackCycleId`; append-time fallback identity and admission validity are immutable repair facts, while the fallback cycle's own later void, migration, Refactor, source-currency, or provenance events may change its ordinary eligibility without invalidating the retirement record or selecting a different fallback; replacement edges are acyclic and one-to-one; duplicate operation IDs, duplicate target dispositions, a replacement claimed by multiple targets, or a repair cycle invalidate only the union of their connected repair components with the exact validator diagnostic `TDD_REPAIR_CHAIN_INVALID: TDD repair evidence has invalid order, hash-chain, operation, or disposition linkage.`; an invalid complete monotonic order log invalidates all repairs and abandonments; repaired targets do not emit their own `TDD_GREEN_MISSING`, stale-parallel, or source-currency diagnostics, but abandoned targets retain all ordinary diagnostics; no repair filters diagnostics for another cycle, requirement, test, CHANGE generation, candidate binding, or parallel assignment; repeated validation over identical evidence returns the same selected cycle and diagnostics.
Requirements: REQ-M5-WAVE1-TDD-001 REQ-M5-WAVE1-TDD-002
ADRs: ADR-0023 ADR-0029
Depends-On: DES-M5-TDD-005 DES-M5-TDD-REPAIR-001 DES-M5-TDD-REPAIR-002

## DES-M5-TDD-REPAIR-004: Confirmed CLI and exact diagnostic contract
Responsibilities: Expose public grammar `tdd repair [test-id]` with normal, resume, and audited abandonment modes; reject malformed or unauthorized requests before domain mutation; serialize stable human and JSON results; and map repair domain failures to exit code 1.
Interfaces: normal mode `tdd repair <test-id> --cycle <cycle-id> (--replacement-cycle <cycle-id> | --retire) --approver <name> --reason <text> --confirm [--root <directory>] [--json]`; recovery mode `tdd repair --resume <operation-id> --confirm [--root <directory>] [--json]`; abandonment mode `tdd repair --abandon-pending <operation-id> --approver <name> --reason <text> --confirm [--root <directory>] [--json]`; repair success JSON `{ repaired: true, replayed: boolean, resumed: boolean, operationId, testId, targetCycleId, disposition: "replacement" | "retirement", replacementCycleId?: string, fallbackCycleId?: string, approver, reason, order }`; abandonment success JSON exactly `{ abandoned: true, replayed, operationId, testId, targetCycleId, failureCause, approver, reason, order }`; text abandonment success `REPAIR ABANDON: PASS operation=<operationId> test=<testId> cycle=<targetCycleId> cause=<failureCause>`; blocking JSON `{ error: { code: "TDD_REPAIR_PENDING", message, details: { operationId, testId, targetCycleId } } }`.
Constraints: normal mode without a positional test ID returns exit 2 `CLI_ERROR: <test-id> is required.`; resume and abandonment forbid a positional test ID; recovery requires `--confirm`, operation ID `^tdd-repair:[a-f0-9]{64}$`, and excludes normal/abandon inputs; exact resume CLI errors are `CLI_ERROR: TDD repair resume requires --confirm.`, `CLI_ERROR: --resume must match ^tdd-repair:[a-f0-9]{64}$.`, and `CLI_ERROR: --resume cannot be combined with repair target or disposition options.`; abandonment requires nonblank approver/reason and `--confirm`, the same operation-ID format, and excludes `--resume` plus normal target/disposition inputs; exact abandonment CLI errors are `CLI_ERROR: TDD repair abandonment requires --confirm.`, `CLI_ERROR: --abandon-pending must match ^tdd-repair:[a-f0-9]{64}$.`, and `CLI_ERROR: --abandon-pending cannot be combined with repair target, disposition, or resume options.`, plus existing required/blank approver and reason errors; every `CLI_ERROR` exits 2 and writes nothing; all `TDD_REPAIR_*` domain failures exit 1; exact pending message is `pending repair <operationId> for <testId>:<targetCycleId> must be resumed or abandoned before TDD evidence can change.`; authorization details are exactly `{ requirementId, domain, status }`, with `domain: null` for empty `approval.domains` and the configured owner otherwise, and status values `missing`, `stale`, `domain-mismatch`; target-invalid details and precedence remain `{ cause, testId, targetCycleId }` with `cycle-not-found`, `cycle-id-ambiguous`, `foreign-operation-scope`, `target-not-parallel-bound`, `target-parallel-binding-not-stale`, `retirement-fallback-missing`, `retirement-fallback-ambiguous`; resume-invalid details are `{ operationId, cause }` with `not-found`, `already-completed`, `journal-invalid`, `identity-mismatch`, `partial-projection-mismatch`; abandon-invalid uses message `<operationId> is not one abandonable pending TDD repair.`, details `{ operationId, cause }`, and closed precedence `not-found`, `already-completed`, `resumable`, `journal-envelope-invalid`, `already-abandoned`; normal precedence is CLI, pending, complete ledger, replay, selector, disposition, authorization, scope, binding/source, stale eligibility, disposition validity; resume precedence is CLI, operation-state lookup, journal identity/schema, partial projection, prospective ledger, completion; abandonment precedence is CLI, operation-state lookup, valid envelope, resume failure classification, replay/conflict, prospective ledger, append; existing writers remain blocked through incomplete abandonment and unblock only after its complete ledger validates.
Requirements: REQ-M5-COMPAT-013 REQ-M5-WAVE1-TDD-001 REQ-M5-WAVE1-TDD-002
ADRs: ADR-0009 ADR-0023 ADR-0029
Depends-On: DES-M5-002 DES-M5-TDD-REPAIR-001 DES-M5-TDD-REPAIR-002
