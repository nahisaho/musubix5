# Multi-CHANGE candidate workspace design

## Architecture constraints

- Control worktree の `.musubix/` を共有 operational state の唯一の保存先とし、
  candidate worktree と integration worktree は source tree と実行 cwd を提供する。
- Candidate-owned projection は
  `.musubix/candidates/candidate-<64-lowercase-hex>/`、integration projection は
  `.musubix/candidates/integrations/integration-<64-lowercase-hex>/`、registry は
  `.musubix/candidates/registry.json`、authoritative chronology は既存の
  `.musubix/journal/normal/` に保存する。Logical ID の `candidate:` /
  `integration:` prefix は evidence と CLI に保持し、filesystem component に
  使用しない。
- Candidate identity は repository identity、CHANGE ID、generation、作成時の
  identity base commit、creation epoch の canonical JSON SHA-256、integration identity、manifest、
  fingerprint は各節で定義する canonical JSON SHA-256 とし、表示用 path や
  wall-clock time を identity に含めない。
- Candidate context は CHANGE ID、positive generation、repository identity、
  immutable base commit、candidate commit の完全一致でのみ evidence credit を得る。
- 単一 CHANGE writer は CHANGE lease の後に repository append lease を取得する。
  multi-CHANGE writer は CHANGE ID 昇順で全 CHANGE lease を取得した後、append lease
  を最後に取得する。逆順取得は禁止する。
- `.musubix/evidence/**`、`.musubix/journal/**`、`.musubix/candidates/**` は
  candidate ownership diff から除外し、integration finalization だけが control
  state から integration worktree へ materialize する。
- `.musubix` と Git common directory の lease file、一時 lock metadata、
  control-worktree locator、finalization marker は fingerprint、
  materialization、commit の対象外とする。
- Selector の欠落、曖昧性、repository/generation/commit mismatch、lease loss、
  ownership conflict、stale dependency、verification failure はすべて fail-closed
  とし、成功形の fallback や自動 conflict resolution を行わない。
- 既存の sole-active CHANGE と one-CHANGE parallel plan は candidate 機能を
  使用しない限り従来の resolution、証跡、exit code、JSON 契約を維持する。

## Candidate lifecycle

`prepared -> active -> ready -> integrating -> verified -> integrated`

Failure and maintenance transitions are:

- Candidate creation journals `prepared` after reserving identity and refs, then
  journals `active` only after the branch, worktree, and registry projection are
  present and revalidated.
- `prepared | active | ready | integrating | verified -> failed`
- `prepared | active | ready | failed -> abandoned`
- `active | ready | failed | integrating | verified -> stale`
- `ready -> active` when approval, TDD, quality, snapshot, gate, configuration,
  or candidate-commit binding drifts without a base change
- `prepared | active | ready | failed | abandoned | stale | integrated -> deleted`
- `stale -> active` only through a successful refresh that creates a new
  candidate commit and invalidates old candidate-bound evidence
- `failed -> active` only after the failed prerequisite is repaired and complete
  readiness re-evaluation succeeds
- `integrating | verified -> ready` when an integration attempt terminates
  without changing candidate bindings
- `integrating | verified -> integrating` only as idempotent resume of the same
  derived integration ID and identical candidate set

Only journaled transitions are authoritative. Registry and candidate projection
files are rebuildable views.

## DES-M5-MULTI-CHANGE-001: Candidate context resolver
Responsibilities: Resolve an explicit candidate or integration context from CLI selectors, registered worktree current directory, and the control root; reject ambiguous implicit selection; expose one normalized execution context to every generation-bound service.
Interfaces: `resolveExecutionContext(root, { changeId?, multiChangeVerification?, cwd?, maintenance? }): CandidateContext | IntegrationContext | RepositoryContext`, `candidateContextForWorkspace(cwd)`, `assertSelectorConsistency(context, root, selectors)`.
Constraints: `--change-id` and `--multi-change-verification` are mutually exclusive; a registered candidate or integration worktree is an implicit explicit selector only when no context flag is present; an explicit context flag and `--root` must identify the same registered context as managed cwd, otherwise `CANDIDATE_WORKSPACE_SELECTOR_MISMATCH`; control-root implicit resolution is allowed only when cwd is outside every registered candidate/integration worktree and preserves sole-active resolution and `CHANGE_GENERATION_MIXED`; malformed user-facing selectors are CLI errors and unknown, deleted, foreign, generation-mismatched, or selector-mismatched contexts persist nothing; abandoned generations reject every pass-producing operation with `CHANGE_GENERATION_PHASE` and permit only show, inspection-only resume, and confirmed cleanup.

## DES-M5-MULTI-CHANGE-002: Candidate registry and state router

`candidate-integration-v1` owns integration ID, starting default commit, ordered input tuples, apply order, deterministic release-owner CHANGE ID, Git-common-directory-relative integration worktree path, source manifest, lifecycle state, report hashes, integration commit, and recovery metadata; `candidate-workspace-tombstone-v1` owns deleted candidate identity, last state, actor, reason, retained branch/commit references, creation epoch, and journal order; registry entries bind repository identity, CHANGE ID, generation, candidate ID, both base roles, branch, Git-common-directory-relative worktree path, state, and latest candidate commit; no absolute machine-local path is persisted; the control root is re-derived from the executing repository Git common directory and the stored relative managed-worktree path, then repository identity is revalidated; candidate paths are normalized descendants of the Git-common-directory managed root and every ancestor is checked against symlink aliasing; `candidateStateRoot` and `integrationStateRoot` are the only projection-root builders, accept branded keys from DES-M5-MULTI-CHANGE-010, and return platform-native absolute paths; owner-specific read/write validates only the selected owner component and ancestors, while integration materialization, staging, commit, and registry rebuild perform the whole-root canonical-member scan; read-only list/show include offending member names in `CANDIDATE_STATE_OWNERSHIP` diagnostics without deleting them; the shared registry is rebuilt from journal records and replaced only while the repository append lease is held; same-directory registry replacement may create only `registry.json.<pid>-<uuid>.tmp`, which is operational metadata rather than a state member, is excluded from fingerprint/materialization/stage/commit, and may be reclaimed as stale only by the append-lease holder after verifying no live writer owns it; candidate projections are sharded by logical candidate owner and never share a mutable file with another candidate; normal journal records retain all owners verbatim while consumers grant credit only to the selected context; registry and projections never replace the journal as authority; terminal integration registrations remain audit records after worktree cleanup; `OperationalStateBaseline` is the sorted path/hash set for `.musubix/evidence/**`, `.musubix/journal/**`, and `.musubix/candidates/**` after excluding lease files, recognized registry temporary files, temporary lock metadata, the control-worktree locator, finalization marker, and temporary files.

## DES-M5-MULTI-CHANGE-004: Candidate workspace lifecycle manager
Responsibilities: Create, show, list, resume, refresh, and safely remove candidate branches and managed worktrees; capture immutable base and dirty-state invariants; validate commit reachability and worktree cleanliness.
Interfaces: `createCandidateWorkspace(changeId)`, `showCandidateWorkspace(selector)`, `listCandidateWorkspaces()`, `resumeCandidateWorkspace(selector)`, `refreshCandidateWorkspace(selector)`, `cleanupCandidateWorkspace(selector, actor)`, shared `evaluateCandidateCleanupPolicy`.
Constraints: At most one live candidate exists per repository identity, CHANGE ID, and generation; under the CHANGE lease, create journals `prepared`, returns the existing live identity with `replayed: true` on exact replay, or derives the creation epoch from authoritative journal records as exactly one plus the maximum creation epoch across every prior candidate and tombstone for the same repository identity and CHANGE ID, then derives a new candidate ID from repository identity, CHANGE ID, generation, identity-base commit, and that epoch, initializes current-base commit to the same value, and journals `active` after worktree and repository revalidation; the rebuildable live registry is never the source of the next epoch; replay of `prepared` uses its saved identity base, current base, branch, relative worktree path, creation epoch, and candidate ID to finish missing branch/worktree creation and transition to `active`, while any conflicting existing ref/path/repository identity fails `CANDIDATE_INTEGRATION_CONFLICT` without deriving a second identity; confirmed cleanup of `prepared` removes only its managed worktree when no unintegrated commit exists, retains the reserved branch/ref, and records the tombstone with its creation epoch; managed worktrees are Git-common-directory descendants outside the control working tree, and their components use validated `CHANGE-<digits>`, `g<positive-integer>`, and lowercase hex suffixes only; create for an abandoned generation fails `CHANGE_GENERATION_PHASE`, create for a deleted same-generation candidate fails `CANDIDATE_WORKSPACE_NOT_FOUND`, and only a new active generation receives a new identity; a deleted namespace is never reused; create leaves every control-worktree path outside `.musubix/journal/**` and `.musubix/candidates/**` byte-for-byte unchanged; refresh accepts CHANGE ID only, derives the patch from current-base commit to candidate tip, applies it to the new default tip, preserves immutable identity-base commit and candidate ID, updates current-base commit and candidate tip atomically, and invalidates evidence bound to the prior current base/tip; evidence binding, staleness, and `candidateChangeSet` use current-base commit, while identity reproduction and audit use identity-base commit; refresh requires prior deletion of a live old-commit snapshot; CHANGE abandon moves a live candidate to abandoned, and reopening creates a new generation whose candidate must be created with a new identity rather than refreshing the abandoned candidate; `DES-M5-CANDIDATE-CLEANUP-001` and ADR-0030 are authoritative for cleanup eligibility and diagnostic precedence. Cleanup first resolves an exact completed-operation-key replay through `DES-M5-CANDIDATE-CLEANUP-004`, returning the recorded result without invoking the predicate. All other inputs are normalized to state, hazard, and reachability facts and delegated to `evaluateCandidateCleanupPolicy`: any `deleted` input fails `CANDIDATE_WORKSPACE_NOT_FOUND` before synthetic hazard fields are considered; universal dirty/untracked/lease/conflict hazards then fail every inspectable non-deleted state; unintegrated `prepared | active | ready` candidates and `integrated` candidates whose commit is not reachable from the default branch fail `CANDIDATE_CLEANUP_UNSAFE`; `integrating | verified` candidates fail `CANDIDATE_INTEGRATION_CONFLICT` regardless of commit reachability; clean reachable `prepared | active | ready | failed | abandoned | stale | integrated` candidates are allowed worktree-only cleanup; and unintegrated `failed | abandoned | stale` candidates are also allowed worktree-only cleanup while retaining branch, commits, and tombstone references.

## DES-M5-MULTI-CHANGE-009: Candidate CLI and compatibility facade

## DES-M5-MULTI-CHANGE-010: Candidate filesystem identity codec
Responsibilities: Convert canonical logical candidate and integration IDs to deterministic cross-platform filesystem keys, validate on-disk owner directory names, normalize platform path failures, and own the three-OS portability acceptance evidence.
Interfaces: `candidateFilesystemKey(candidateId): CandidateFilesystemKey`, `integrationFilesystemKey(integrationId): IntegrationFilesystemKey`, `logicalOwnerFromFilesystemKey(key): CandidateId | IntegrationId`, `inspectCandidateStateMembers(root): CandidateStateMemberReport`, `assertCanonicalCandidateStateMembers(root): void`, `normalizeCandidatePathError(error): CandidateStateOwnershipError`.
Constraints: `CandidateFilesystemKey` and `IntegrationFilesystemKey` are branded values constructible only by this codec; raw strings cannot be passed to projection-root or managed-integration-worktree builders; the codec accepts only `candidate:[0-9a-f]{64}` or `integration:[0-9a-f]{64}` and performs a reversible prefix substitution to `candidate-<same-hex>` or `integration-<same-hex>`; candidate keys are exactly 74 characters and integration keys exactly 76 characters; the REQ-M5-MULTI-CHANGE-004 length bounds apply to the owner projection roots `.musubix/candidates/<candidate-key>` and `.musubix/candidates/integrations/<integration-key>`, not their `evidence/` or `reports/` descendants; every root builder validates repository-relative owner-root length before filesystem access; platform path-API rejection during create, read, resume, materialize, stage, or commit is normalized to `CANDIDATE_STATE_OWNERSHIP`, and only partial directories proven to have been created by the current failed operation are removed; logical IDs remain unchanged in registry, journal, evidence, JSON, and diagnostics; `.musubix/candidates/` recognizes `registry.json`, `integrations/`, canonical candidate keys, and the operational temp grammar `registry.json.<pid>-<uuid>.tmp`, while `integrations/` recognizes only canonical integration keys; owner-specific access validates the selected path, whole-root validation runs before registry rebuild/materialize/stage/commit, and inspection reports offending members for manual remediation without deleting unknown state; `TEST-M5-CANDIDATE-PATH-PORTABILITY-001` runs in the exact REQ-M5-CI-001 Ubuntu/Windows/macOS Node 24 matrix, asserts byte-identical keys, native absolute projection roots, encoded managed integration-worktree paths, create/read/resume/materialize/integration-commit/fresh-checkout success, zero colon-bearing candidate/integration components in `git ls-tree -r`, and zero colon-bearing managed worktree components.
