# Multi-CHANGE candidate workspace requirements

## REQ-M5-MULTI-CHANGE-001: Create isolated candidate workspaces
Priority: must
Type: functional
Pattern: event-driven
Statement: 複数のactive CHANGEのうち1つに対して候補作成を要求したとき、システムはそのCHANGE専用の候補branch、管理worktree、不変base commit、および一意なcandidate identityを作成し、control worktreeと他候補の内容を変更してはならない。
Acceptance: 同じrepository commitをbaseとして2つのactive CHANGE候補を作成すると、異なるcandidate identity・branch・worktree pathが返り、各候補に同じbase commitと対応するCHANGE ID/generationが保存されること。candidate IDはrepository identity・CHANGE ID・generation・base commit・そのCHANGEで過去のtombstoneを含む最大値より1大きいpositive creation epochを持つcanonical JSONのSHA-256から`candidate:<64-lowercase-hex>`として導出すること。prepared・active・deleted tombstoneの各authoritative journal recordはcreation epochを保持し、次epochはrebuild可能なlive registryではなく同じrepository identity・CHANGE IDのこれら全recordからexactly `max + 1`として計算すること。createはGit common directory配下かつcontrol working tree外のmanaged rootへworktreeを作成し、journal済み`prepared`からworktree・repository identity・branchを再検証した後だけ`active`へ遷移してactive recordを返すこと。同じlive candidateの再作成はexit 0で保存済みidentityと`replayed: true`を返して新規writeを行わないこと。abandoned generationのcreateはexit 1 `CHANGE_GENERATION_PHASE`、deleted candidateと同じgenerationのcreateはexit 1 `CANDIDATE_WORKSPACE_NOT_FOUND`で何も作成せず、新しいactive generationだけが増加したcreation epochを持つ新identityを作成できること。作成前後でcontrol worktreeの`.musubix/journal/**`と`.musubix/candidates/**`以外のtracked・staged・untracked・deleted path状態が完全一致し、その2つの宣言済みstate pathだけにregistry/journal recordが追加され、候補一覧と再開操作が保存済みidentityを返すこと。
CLI: `candidate-workspace create --change-id <id>`はactive CHANGEとそのpositive active generationを明示選択し、同一repository identity・CHANGE・generation当たり高々1つのlive candidate workspaceを作成する。`candidate-workspace list`と`candidate-workspace show <change-id-or-candidate-id>`はread-onlyであり、同じidentityの再作成は既存recordを返す。

## REQ-M5-MULTI-CHANGE-002: Resolve only explicit candidate context
Priority: must
Type: functional
Pattern: state-driven
Statement: 複数のactive CHANGEが存在する間、システムはCHANGE IDまたはcandidate workspaceで明示された候補contextもしくはintegration IDまたはintegration workspaceで明示されたintegration contextだけを解決しなければならない。
Acceptance: 2つ以上のactive CHANGEが存在するfixtureで、`--change-id <id>`または登録済みcandidate worktree current directoryで明示選択したapproval・TDD・gate・status操作は選択候補だけを対象として決定的に成功または対象候補固有の理由で失敗すること。候補選択を省略したstate-changing操作とgateはexit 1 `CHANGE_GENERATION_MIXED`を返して何も永続化せず、statusはexit 0で`ready: false`と同diagnosticを返すこと。REQ-M5-LIFECYCLE-005のread-only maintenanceとnon-credit audit例外は維持すること。不明または削除済み候補はexit 1 `CANDIDATE_WORKSPACE_NOT_FOUND`、foreign repositoryはexit 1 `CANDIDATE_WORKSPACE_REPOSITORY_MISMATCH`、generation不一致はexit 1 `CANDIDATE_WORKSPACE_GENERATION_MISMATCH`、workspace/change-id不一致はexit 1 `CANDIDATE_WORKSPACE_SELECTOR_MISMATCH`を返し、malformed user-facing selectorはexit 2 `CLI_ERROR`を返すこと。current directoryが登録済みcandidateまたはintegration worktree内にある場合、そのworkspace contextを暗黙selectorとして使用できるのは明示context flagがないときだけであり、`--change-id`、`--multi-change-verification`、または`--root`がcurrent workspaceと異なるcandidate、integration、またはcontrol rootを選択する場合はexit 1 `CANDIDATE_WORKSPACE_SELECTOR_MISMATCH`で何も永続化しないこと。同じcontextを明示するflagと`--root`は許可すること。current directoryが登録済みcandidate/integration worktree外にあり、`--root`がcontrol rootを指し、`--change-id`と`--multi-change-verification`を省略した場合だけimplicit resolutionを使用すること。approval prepare/record/validateの全stage、TDD、gate、statusはvisible `--change-id <id>`を支持し、workflowは既存の`--change-id`を維持すること。candidate contextを選択する`--change-id`を持たないgeneration-bound commandは登録済みcandidate worktree current directoryを明示selectorとして認めること。これとは別に、registered integration worktree current directoryまたは`--multi-change-verification <integration-id>`はintegration setを選択する明示contextであり、trace・graph・gate・statusはconflicting registered workspace current directoryがない場所から同じintegration IDを受け付け、orchestratorが起動するconfigured commandは同contextのsource rootを継承すること。`--change-id`と`--multi-change-verification`の同時指定はexit 2 `CLI_ERROR`で何も永続化しないこと。いずれの明示contextもないcontrol root実行だけがimplicit resolution規則に従うこと。

## REQ-M5-MULTI-CHANGE-003: Bind evidence to one candidate
Priority: must
Type: functional
Pattern: ubiquitous
Statement: システムはcandidate context内で生成または評価するapproval、TDD、trace、graph、formal、performance、quality、gate、status、workflow、およびattestation証跡を、そのCHANGE ID、generation、repository identity、base commit、およびcandidate commitへ結合しなければならない。
Acceptance: CHANGE Aで記録した各証跡をCHANGE Bのgateへ提示してもBの必須checkを満たさず、exit 1 `CANDIDATE_EVIDENCE_MISMATCH`で拒否されること。candidate commit、generation、approval hash、configuration fingerprint、trace/graph input、test report、workflow transcript、attestation payloadのいずれかを変更すると既存評価がstaleになり、再評価前のstatusはreadyにならないこと。

## REQ-M5-MULTI-CHANGE-004: Enforce candidate state ownership
Priority: must
Type: functional
Pattern: state-driven
Statement: candidate workspaceが選択されている間、システムはcandidate-ownedな`.musubix`状態を共有control state内の明示されたcandidate partitionへrouteし、他候補のpartitionを読み書きしてはならない。
Acceptance: 共有operational state rootはcontrol worktreeの既存`.musubix/`であり、candidate registryは`.musubix/candidates/registry.json`、candidate projectionは`.musubix/candidates/<filesystem-key>/`、integration projectionは`.musubix/candidates/integrations/<filesystem-key>/`、normal journalは既存`.musubix/journal/normal/`を使用し、mode切替またはjournal migrationを行わないこと。candidate contextはsource treeを登録済みcandidate worktreeから解決し、共有control rootは保存済みGit-common-directory-relative worktree pathと実行repositoryのGit common directoryから導出してrepository identityを再検証し、registryへmachine-local absolute control rootを保存しないこと。registry・lease・journal・candidate projectionはその導出済みcontrol rootから解決すること。2候補を交互または並行に操作するtestで、各候補のapproval/TDD/quality/workflow state fingerprintとjournal ownershipが相互に不変であること。repository-wide normal journalはREQ-M5-LIFECYCLE-002の単一orderとhash chainを維持し、各candidate-owned recordへcandidate ID・CHANGE ID・generation・repository identityを保存すること。各single-CHANGE writerはCHANGE lease取得後にrepository-scoped append leaseを最後に取得し、multi-CHANGE writerはaffected CHANGE leasesをCHANGE ID昇順で全取得した後にappend leaseを取得してorder割当・`previousSha256`導出・record writeの完了まで保持すること。CHANGE lease timeoutは何も永続化せずexit 1 `CANDIDATE_LEASE_BUSY`、append lease timeoutはexit 1 `CANDIDATE_JOURNAL_BUSY`を返すこと。2つ以上のCHANGEに対する8 concurrent writer fixtureはintegration finalizationを同時実行しない独立fixtureとしてgapとduplicateのない有効なhash chainを作り、各成功invocationをexactly onceで記録すること。finalization中にappend leaseを取得できない別writerはconfigured timeout後に`CANDIDATE_JOURNAL_BUSY`で停止し、自動retryまたは部分writeを行わないこと。candidate commitのownership/conflict計算からgenerated operational paths `.musubix/evidence/**`・`.musubix/journal/**`・`.musubix/candidates/**`を除外し、integrationだけがcontrol rootのこの3 pathをintegration worktreeへ決定的にmaterializeすること。normal journalは他candidate recordを含む全recordをorder順にverbatimでmaterializeしてhash chainを維持し、projectionとevidenceも全ownerを保存するが、選択外candidateのrecordはintegration verificationへcreditを与えないこと。integration finalizationはrepository append leaseを取得して最終verified recordをappendした後、その時点の3 materialized path setだけからcontrol-state fingerprint baselineを取得し、同leaseを保持したままoperational stateのmaterialize・integration commit作成・同じpath setのfingerprint再照合・default branch fast-forward・integrated transition appendを行うこと。fingerprint driftは何も更新せずexit 1 `CANDIDATE_OPERATIONAL_STATE_DRIFT`で停止し、入力candidateをstaleにせず、同じintegration IDの明示retryだけを許可すること。`.musubix`またはGit common directory内のlease fileと一時lock metadataはmaterializeおよびcommit対象から除外すること。他candidate pathへのsymlink/alias、owner不一致record、同一candidateへのfenced lease違反はexit 1 `CANDIDATE_STATE_OWNERSHIP`でfail-closedになり、候補間でjournalをcopyまたはmergeしないこと。logical candidate IDは`candidate:<64-lowercase-hex>`、logical integration IDは`integration:<64-lowercase-hex>`のままregistry・journal・evidence binding・CLI/JSON identity fieldへ保存し、単一のencoderがそれぞれ`candidate-<same-64-lowercase-hex>`と`integration-<same-64-lowercase-hex>`へ全単射で変換すること。candidate keyは74文字、integration keyは76文字で、両者は`^(candidate|integration)-[0-9a-f]{64}$`に一致し、Windows禁止文字、control character、末尾dot/space、reserved device name、`.`、`..`を含まないこと。生成するrepository-relative owner projection rootはcandidateで95文字以下、integrationで112文字以下とし、これを超えるrootまたはplatform path APIが拒否するrootはpartial directoryを残さずexit 1 `CANDIDATE_STATE_OWNERSHIP`で停止すること。internal encoder入力またはon-disk owner directoryがexact logical-ID/key形式でない場合、非canonical caseの場合、または候補種別とprefixが一致しない場合はfilesystemを変更せずexit 1 `CANDIDATE_STATE_OWNERSHIP`で拒否し、user-facing selector syntax errorはREQ-M5-MULTI-CHANGE-002のexit 2 `CLI_ERROR`を維持すること。`.musubix/candidates/`直下は`registry.json`、`integrations/`、`candidate-<64-lowercase-hex>/`だけをstate memberとして認識し、`integrations/`直下は`integration-<64-lowercase-hex>/`だけを認識すること。literal logical ID、colonを含むcomponent、その他noncanonical owner directoryを作成、read fallback、materialize、stage、commitしてはならず、検出時はexit 1 `CANDIDATE_STATE_OWNERSHIP`でfail-closedになること。in-processで返すprojection rootはplatform-native absolute pathとし、永続recordへmachine-local absolute rootを保存しないこと。Node.js 24のUbuntu・Windows・macOS matrixで同一logical IDからbyte-exactに同一filesystem keyを得て、candidate/integration projectionとmanaged integration worktreeのcreate・read・resume・materialize・integration commit・fresh checkoutが成功し、committed treeおよびmanaged worktreeにcolonを含むcandidate/integration componentが0件であること。

## REQ-M5-MULTI-CHANGE-005: Detect dependencies and ownership conflicts
Priority: must
Type: functional
Pattern: event-driven
Statement: 候補の統合準備を開始したとき、システムは各候補の変更pathと明示依存関係とcandidate commit到達可能性と既統合状態を不変baseに対して評価して統合前に競合またはstale dependencyを検出しなければならない。
Acceptance: 同一pathを変更する2候補は統合開始前にexit 1 `CANDIDATE_OWNERSHIP_CONFLICT`で停止し、ファイル内容を自動選択・結合しないこと。未完了依存は`CANDIDATE_DEPENDENCY_UNSATISFIED`、循環依存は`CANDIDATE_DEPENDENCY_CYCLE`、base不一致または依存candidate commit更新は`CANDIDATE_BASE_STALE`、到達不能commitは`CANDIDATE_COMMIT_UNREACHABLE`、既統合候補の再投入は`CANDIDATE_ALREADY_INTEGRATED`としてexit 1で停止すること。変更pathが重ならず依存順が満たされる候補だけがcandidate IDをtie-breakerとするstable topological orderを得ること。

## REQ-M5-MULTI-CHANGE-006: Integrate and reverify deterministically
Priority: must
Type: functional
Pattern: event-driven
Statement: 競合のない候補集合の統合を開始したとき、システムは保存済み順序とcandidate commitだけを使用してcleanなintegration worktreeへ決定的に適用し、統合結果を完全検証しなければならない。
Acceptance: `candidate-workspace integrate <change-id-or-candidate-id...> --confirm`は1つ以上のready candidateを明示選択し、common `--root`と`--json`を支持すること。integration IDはrepository identity・開始default branch commit・candidate ID順に並べたCHANGE ID/generation/candidate ID/candidate commitのcanonical JSON SHA-256として決定的に導出すること。`integration-source-manifest-v1`はcandidate commitsの適用後かつoperational state materialization前のintegration treeから`.musubix/evidence/**`・`.musubix/journal/**`・`.musubix/candidates/**`を除外したREQ-M5-WORKTREE-005形式のcanonical projectionであり、同じbase・candidate commits・依存graphを2回評価すると同じintegration ID・統合順序・consumed commit sequence・integration-source-manifest SHA-256を得ること。選択されたready candidate集合は1つのintegration attemptで現在のdefault branch tipからclean integration worktreeへ適用し、Git conflict、dirty integration tree、予期しないcandidate tip移動はexit 1 `CANDIDATE_INTEGRATION_CONFLICT`で停止すること。integration worktreeはintegration ID・選択candidate IDs・CHANGE IDs・generations・input commitsを持つ一時的なregistered integration contextとして共有stateへ記録し、trace・graph・`gate --changed --multi-change-verification <integration-id>`・`status --multi-change-verification <integration-id>`はimplicit CHANGE resolutionを使用せずその集合だけを評価すること。configured required commands・strict trace・graph gateはすべてpassしなければならない。multi-change verification中のapprovalおよびcandidate-gate diagnostic producerは原因判定時にregistered `Diagnostic.detail`を必ず設定し、各registered code/detail pairを発生させる回帰testはgate projectionまでそのdetailが保持されることを検証しなければならない。changed gateではrequired `approval` checkだけがfail可能であり、その全diagnosticが次のexact code/detail pairの閉集合に属する場合に限り許容すること: `APPROVAL_CANDIDATE_MISSING/integration-candidate-snapshot-missing`、`RELEASE_GATE_EVIDENCE_MISSING/integration-candidate-gate-missing`、`RELEASE_GATE_EVIDENCE_STALE/integration-candidate-context-mismatch`、`RELEASE_GATE_CANDIDATE_MISMATCH/integration-candidate-context-mismatch`、`APPROVAL_MISSING/integration-release-approval-missing`、`APPROVAL_STALE/integration-release-approval-stale`。最後の2 pairはsource approval stageが`release`でdomainなしの場合だけ生成し、requirements・design・domain approvalへ付与してはならない。空diagnostic set、detail欠落または不一致、`APPROVAL_CANDIDATE_UNAVAILABLE`、`RELEASE_CANDIDATE_TREE_MISMATCH`、`CHANGE_GENERATION_INCOMPLETE`を含むその他の`approval` diagnostic、他checkのfail、required check/commandのskipped・absent、またはmalformed outcomeはexit 1 `CANDIDATE_INTEGRATION_VERIFICATION_FAILED`として成功を記録しないこと。statusはexit 0・`ready: false`でなければならず、この許容はcandidate gate・release approval・publication readinessのcreditを与えないこと。closed verification policyを満たした場合だけintegration stateをverifiedへ遷移し、verified recordは開始default branch commit・入力candidate commits・順序・integration-source-manifest SHA-256・各report hashへ結合すること。verifiedからintegratedへの遷移はdefault branch tipが開始commitと一致する場合のatomic fast-forward成功時だけ記録し、tipが進んでいた場合は何も更新せずexit 1 `CANDIDATE_BASE_STALE`として入力候補をstaleにすること。fast-forward前にGit common directoryへintegration ID・integration commit・開始default branch commit・current append-lease contextのfinalization tokenへ結合したuntracked finalization markerを保存し、fast-forward後にappendするintegrated transition recordは同じrepository append leaseを保持したままintegration commitとmaterialization後のcandidate-tree-manifest SHA-256へ結合し、integration commit自身にはそのpost-commit recordまたはmarkerを含めないこと。resumeは新しいlease contextが保存済みfinalization lease setと同じCHANGE集合・昇順を持ち、各fencing tokenが保存値以上であることを検証し、marker tokenは保存済みfinalization tokenと一致しなければならないこと。marker存在時にdefault refが開始commitならmarkerを削除してpre-fast-forward状態へ戻し、同じintegration IDのfinalizationを再実行すること。default refがintegration commitなら必要に応じてcontrol worktreeを同commitへrefreshし、integrated transitionをexactly onceでappendしてmarkerを削除すること。default refがそれ以外ならmarkerを削除し、何も追加更新せずexit 1 `CANDIDATE_BASE_STALE`として入力候補をstaleにすること。marker schema、integration ID、開始commit、integration commit、lease set/order/token lineage、またはcommit reachabilityの不一致はmarkerを保持してexit 1 `CANDIDATE_INTEGRATION_CONFLICT`でfail-closedになること。正常なintegrated append後とpre-fast-forward rollback後はmarkerが存在せず、別integration attemptはterminal markerがない場合だけ開始できること。integrationまたはrefreshによりcandidate commitとverified integration commitが異なる場合、旧commitへ結合されたrelease approval・candidate gate・attestationをstaleにし、default branchから到達可能なverified integration commitに対する再評価とrelease再承認を要求すること。

## REQ-M5-MULTI-CHANGE-007: Resume and clean up safely
Priority: must
Type: functional
Pattern: unwanted-behavior
Statement: もし候補操作が中断状態・失敗状態・abandoned状態・completed状態のいずれかならば、システムは永続registryとjournalから状態を再構築して未統合変更を暗黙に削除せずに再開またはcleanupしなければならない。
Acceptance: candidate stateは`prepared | active | ready | integrating | verified | integrated | failed | abandoned | stale | deleted`のいずれかであり、journal済みtransitionだけを再構築すること。`candidate-workspace ready <change-id-or-candidate-id>`はcommon `--root`と`--json`を支持し、current requirements/design approvals、complete TDD、terminal full-set quality、clean reachable candidate tip、sole current candidate snapshot、およびcomplete passing candidate gateをすべて再検証してactiveからreadyへのtransitionとそのbinding inputsを記録し、release approvalを前提にしないこと。これらのbinding driftはreadyをactiveまたはstaleへ戻し、required verification failureはfailedへ遷移させること。`candidate-workspace resume <change-id-or-candidate-id>`はcommon `--root`と`--json`を支持し、process再起動後も同じcandidate identity、base、branch、worktree、generation、最後の有効transitionを返すこと。integratingまたはverified stateの同じ導出integration ID・same candidate set再実行はjournal済みprogressを再利用してverificationまたはdefault-branch fast-forwardをidempotentに完了し、異なるcandidate setは`CANDIDATE_INTEGRATION_CONFLICT`で停止すること。`CANDIDATE_ALREADY_INTEGRATED`はintegrated candidateの再投入だけに適用すること。別候補の統合でdefault branchが進んだ未統合候補は`stale`となり、`candidate-workspace refresh --change-id <id>`がCHANGE IDだけをselectorとして受け付け、clean worktreeで旧baseからの候補差分を新baseへ適用して新candidate commitを作成し、旧candidate-bound evidenceをstaleにして完全再検証を要求すること。refreshがcandidate IDを受け付けない制約は新candidate commitへidentity bindingを更新する操作をCHANGE generation単位に限定するためである。refresh conflictは`CANDIDATE_INTEGRATION_CONFLICT`で停止してhistoryを書き換えないこと。旧commitにlive candidate snapshotが存在するrefreshはREQ-M5-WORKTREE-007の明示delete後だけ許可し、status guidanceはdelete後のsnapshot再作成を示すこと。dirty、untracked、実行中lease、または未解決conflictを持つcleanupは全stateでexit 1 `CANDIDATE_CLEANUP_UNSAFE`となること。未統合commitを持つ`prepared | active | ready`候補は`CANDIDATE_CLEANUP_UNSAFE`、`integrating | verified`候補は`CANDIDATE_INTEGRATION_CONFLICT`で拒否すること。未統合commitを持つ`failed | abandoned | stale`候補はconfirmed cleanupでmanaged worktreeだけを削除でき、branch、commit、registry history、およびtombstone referenceを保持すること。`integrated`候補はcommit到達可能性と通常のcleanliness条件を満たす場合にcleanupでき、`deleted`候補への再cleanupは完了済み同一operation keyのexact replayを除き`CANDIDATE_WORKSPACE_NOT_FOUND`で0 writeとなること。`candidate-workspace cleanup <selector> --deleted-by <name> --confirm`だけが対象candidateを削除し、REQ-M5-WORKTREE-007と同じappend-only audit原則のtombstoneを残して他候補とcontrol worktree contentを変更しないこと。abandoned generationのpass-producing操作は`CHANGE_GENERATION_PHASE`で停止し、show/resume-for-inspection/confirmed cleanupだけを許可すること。

## REQ-M5-MULTI-CHANGE-008: Preserve single-CHANGE and parallel compatibility
Priority: must
Type: functional
Pattern: optional-feature
Statement: multi-CHANGE candidate機能を使用しない場合、システムは既存の単一active CHANGE workflow、`CHANGE_GENERATION_MIXED` fail-closed規則、および1 CHANGE内のparallel plan/assignment/integration履歴との互換性を維持しなければならない。
Acceptance: 既存のsingle-CHANGE、candidate snapshot、parallel plan、assignment、integration、release approval test suiteが変更なしでpassすること。明示selectorなしの既存commandはactive CHANGEが1件なら従来と同じcontextを選択し、2件以上ならREQ-M5-MULTI-CHANGE-002のexit/status規則に従うこと。選択済みcandidate context内ではparallel integration verification、candidate snapshot、candidate gate、release approval、status readinessが他のactive CHANGEの存在だけを理由にnon-currentまたはnon-readyにならないこと。parallel assignment evidenceは親CHANGE candidateだけに所属し、別CHANGEのcandidate evidenceとして使用できないこと。`candidate-snapshot create <change-id>`はcontrol rootでは従来のsole-active confirmation-token規則を維持し、登録済みcandidate worktree内ではworkspaceが選択したCHANGEとのbyte-exact confirmationとして動作すること。
